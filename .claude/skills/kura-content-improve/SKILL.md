# KuraSelect 記事改善ルーチン

**このスキルの目的は「凍結や禁止日を踏まずに、読者の役に立つ加筆を少しずつ積むこと」。** 検索指標が上がることは期待しない（図解9本も定型H2 置換も判定不能かサイト並み以下だった）。提案の価値は、ルールを全部確かめたうえで、その日に安全にやれる記事と型を選んでいることにある。

流れは **集める → ふるい分ける → 提案して止まる → 承認分だけ実施 → 記録**。提案のあと、ユーザーの判断を待たずに記事を編集しない。

全面改稿を頼まれたときは §9 だけに従う（§3〜§5 の型の選び方・「足すだけ」の制約は使わない。§0・§2・§6・§8 は §9 の中で読み替えて使う）。

## 0. 前提の確認（ここを飛ばさない）

1. `docs/CONTENT_IMPROVEMENT_CATALOG.md` と `docs/CONTENT_IMPROVEMENT_LOG.md` があるか確認する。無ければ止まってユーザーに伝える（docs/ は gitignore 済みで、別 PC には無いことがある）
2. `reports/weekly/` の最新の `snapshot-<確定日>.md` の確定日を見る。**確定日が7日より前なら `pnpm weekly:snapshot` の実行を促す**（実行するかはユーザーに聞く。古いまま進めるなら提案の冒頭にその旨を書く）
3. 今日がデプロイ禁止日かを確かめる。禁止日は一覧が無く TODO §3 の備考欄に散らばっているので、`grep -n "禁止日" docs/TODO.md` で全件拾い、今日の日付と「〜デプロイ日」（日付未定のものはそのデプロイが今日予定か）を突き合わせる。禁止日でも提案と実施（コミットまで）はしてよいが、**push は禁止日を避ける**と提案に書く
4. 今日が月曜なら、cron（`update-products.yml`・03:00 UTC＝12:00 JST）が bot コミットを積む。**push は 12:00〜13:00 JST を避け、push の直前に `git pull --rebase` で bot コミットを取り込む**と提案に書く

## 1. 集める（この順序で読む）

| # | 参照先 | 何を取るか |
|---|---|---|
| 1 | `docs/CONTENT_IMPROVEMENT_CATALOG.md` | 型（T1〜）・点数・書き方・禁止事項・不採用の型 |
| 2 | `docs/CONTENT_IMPROVEMENT_LOG.md` | 記事ごとの最終実施日と入れた型、§2 の見送り記録 |
| 3 | `data/measurement-holds.json` ＋ メモリ `project_measurement_holds` | 凍結中の記事・対照群・解除日。**両方を見る**（対象と日付は JSON が正） |
| 4 | `data/noindex-articles.json` | noindex にした記事（加筆の対象にしない） |
| 5 | `docs/TODO.md` §3 カレンダー | デプロイ禁止日、日付つきで止められている記事（例: 計画書5 規則1 の7本は 11-05〜）、決まっている加筆の予定 |
| 6 | 最新の `reports/weekly/snapshot-*.md` §2・§3 | 表示の多いページ（上位20）・上位クエリ。§5 の Bing はサイト合計だけで記事別は無い |
| 7 | 最新の `reports/gsc-harvest/harvest-*.md` | テコ入れ候補（あれば） |
| 8 | `bing_page_stats`（MCP・直近4週・`rowLimit: 400`） | Bing の記事別の表示・クリック（週次の行。記事ごとに4週分を足す） |

GSC の数字はこの表の #6 のスナップショットを使う。**提案までに MCP で取るのは #8 の Bing（1回）と、候補に残った記事（最大3本）の T1 用クエリだけ**（§3-2）。T1 の疑問リスト用の全期間クエリは、承認された記事についてだけ §5 で取る。

## 2. ふるい分ける（候補から外す記事）

次のどれかに当たる記事は提案しない。外した理由はまとめて1行で書けばよい。

- 凍結中（対照群を含む）。`releaseDate > 今日` の行の slug
- noindex 中
- `docs/TODO.md` §3 で日付つきで止められている（その日付を書いて次回以降に送る）
- `docs/TODO.md` §3 で**進行中の計画書の測定対象（前窓・後窓）に入っている記事**。凍結台帳の外で測っているもの（例: 計画書2 第1段の §5 #8 スニペット上位5本・§5 #9 Bing 上位5本）は、TODO に停止日が書かれていなくても後窓が終わるまで外す。後窓の終わりが未確定なら「後窓未確定」と書いて外す
- 実施ログで**最終実施から14日以内**（T10 を含む。再クロールと読み込みを待つ。同じ記事に続けて手を入れない）
- 実施ログ §2 で見送られ、理由がまだ解消していない記事×型
- `draft: true` の記事

## 3. 候補を選ぶ

### 3-1. 記事の優先順

上から順に候補を取り、ふるい分けを通った記事を最大3本まで選ぶ。

1. **`docs/TODO.md` で加筆がすでに決まっている記事**（計画書5 の残りなど）で、解禁日が来たもの
2. **表示はあるのに本文が検索に答えていない記事**: スナップショット §2・§3 で表示が多い、または harvest でテコ入れ候補に挙がった記事
3. **Bing で表示がある記事**（§1 の #8。Bing は送客の第1チャネル。メモリ `project_bing_channel_202608`）
4. 上で埋まらなければ、型に合う記事（T3 なら互換が要る商品、T4 なら洗剤・薬剤系）

### 3-2. 記事の状態を確かめる

候補の記事ファイル（`src/content/articles/<slug>.md`）を見て、入れる型を決める。全文を読まず、まず見出しと既存の加筆の有無を確かめる:

```bash
grep -n -E "^#{2,3} |<figure>|^faqs:|^  - question:" src/content/articles/<slug>.md
grep -n -E "^#{2,3} .*(失敗|注意|読み分け)" src/content/articles/<slug>.md
```

2行目に当たれば T2 / T5 は入っている（地の文の「失敗」を拾わないよう、見出しに絞っている）。`<figure>` があれば T6 か T7 が入っている。

- すでに入っている型は選ばない（図解がある記事に T6 を重ねない等）
- **T10 は提案しない**（`kura-trend-topics` が扱う）
- T1 を選ぶときだけ、GSC を `dimensions:["query"]`・`filterPage: https://www.kura-select.com/articles/<slug>/` で取る。期間は直近28日で、**終端はスナップショットの確定日**（確定日を叩き直さない）。疑問の形をしたクエリが無ければ T1 は選ばない
  - `docs/CONTENT_IMPROVEMENT_LOG.md` §3 で有効な話題枠の「話題の言葉（表記ゆれ）」を含むクエリと、**直近3か月**のログ §1 の T10 の行（内容の先頭のラベルが `見直し→一般化` / `見直し→削除` / `期限切れ→一般化` / `期限切れ→削除`）に書いた話題の言葉を含むクエリは、**その枠・行と同じ slug の記事で** T1 の根拠に使わない（T10 と T1 で同じクエリを取り合わない。消した内容を T1 で作り直さない）。別の記事の T1 は止めない。型 `T10集計` の行は対象外
- 1記事に入れる型は2つまで（T5＋T2 のような組み合わせ）

## 4. 提案して止まる

チャットに次の形で出す。ファイルは作らない。

```
## 今日の記事改善の提案（YYYY-MM-DD）

前提: スナップショット確定日 YYYY-MM-DD ／ 今日の push: 可・不可（理由）

| # | 記事 | 型 | この記事を選んだ理由 | 書く内容（見出し案） | 手間 | 注意 |
|---|---|---|---|---|---|---|
| 1 | ... | T1＋T2 | 「〜 違い」で表示 N/28日・本文に答えなし | ## 〜と〜の違い ／ ### 失敗例3つ | 小 | FAQ は frontmatter に |

候補から外した記事: 凍結中 N本、14日以内に実施 N本、TODO で停止中 N本（〜は 11-05〜）

カタログ外の案: なし（あれば、点数・手間・向いている記事・禁止事項の案を添える）
```

- **提案は3件まで。** 4件目以降は書かない
- 点数はカタログの値をそのまま使う。記事ごとに点数を作り直さない
- カタログ外の案は1件まで。**カタログに勝手に足さない**（カタログ §4）
- 出したら止まり、ユーザーの判断（どれをやるか・見送るか）を待つ

## 5. 承認された分だけ実施する

1. **1記事1コミット。** 編集の前に記事を Read する（CLAUDE.md §13）
2. **T1 は疑問リストを作ってから書く。** GSC を `dimensions:["query"]`・`filterPage`・`rowLimit: 5000` で取れる全期間（`startDate` は16か月前・終端はスナップショットの確定日）取り、Bing は `bing_page_query_stats`（`page` に URL・`rowLimit: 400`）で取ってクエリごとに足す。読者の疑問に束ねて表示の多い順に並べ、各項目に根拠（クエリと表示数）を付ける。足す H2・FAQ はこのリストの項目に対応させ、対応しない見出しは足さない。§3-2 の T10 との取り合いの除外はここでも守る
3. **新しい事実を断定する加筆（T1・T2・T3・T4・T6 など、商品・成分・規格・使い方・安全に触れるもの）は、書く前に集める。** `../kura-article-create/references/article-research.md`（共通手順）§1〜§2 に従い、必要な商品ページ・レビュー・メーカーや公的機関の資料をサブエージェント（sonnet）に集めさせ、収集ファイルにある事実だけを書く。楽天を WebFetch で読まない
4. **書いたら別のサブエージェントに照合させる。** 共通手順 §4 に従い、本文を書いていない担当（sonnet 以上）に、足した節と FAQ を収集ファイル・出典・`products[]` に照らして確かめさせ、指摘を直す。既存の情報の並べ替えだけの型（T5・T9）は収集を省いてよいが、照合は行う
5. カタログの各型の「書き方」「禁止」に従う。共通の注意:
   - 本文と `faqs[].answer` に価格・単価・件数・順位を書かない。数値は「ページ上部の比較表（自動更新）でご確認ください」で誘導する（CLAUDE.md §5.0.1）
   - 本文の太字は、閉じる `**` の直前が約物なら `<strong>` で書く。`faqs[].answer` は `**` のまま（メモリ `feedback_markdown_bold_cjk`）
   - 効果効能を断定しない。「最安」「No.1」は根拠が無ければ書かない（CLAUDE.md §11）
   - 既存の本文・見出しは書き換えない。足すだけにする（書き換えが要るならユーザーに確認）
6. 凍結中の記事を Edit しようとして hook（`freeze-guard`）が止めたら、作業を止めてユーザーに伝える（ふるい分けの漏れ）
7. `pnpm content:stamp` を実行し、更新された台帳 `data/content-dates.json` を**加筆と同じコミット**に入れる。`pnpm test` と `pnpm build` を通す（本文 lint・Zod・OGP・台帳）。出力が長いのでサブエージェント（haiku か sonnet）に任せてよい（メモリ `feedback_token_saving_subagents`）。どの担当にも共通手順 §1（本番を開かない／アフィリエイトリンクを踏まない／楽天を WebFetch で読まない）を伝える
8. 図や表を足したら、`pnpm preview` の localhost で幅 375px の表示（あふれ）を確かめる。本番は開かない
9. コミットメッセージは日本語で、「<slug> に <何を> を加筆」の形にする
10. push はユーザーの指示があってから。禁止日は避ける

## 6. 記録する

実施したら、同じ作業の中で:

1. `docs/CONTENT_IMPROVEMENT_LOG.md` §1 の**先頭**に1行足す（日付・slug・型・内容・コミット・登録リクエスト＝「未」）
2. 見送り・却下された提案は §2 に1行足す（日付・記事・型・判断・理由）
3. push とデプロイの完了後に、次の2つを行う
   - **IndexNow を送る**（Bing 向け・AI が実行してよい）: `pnpm indexnow -- --url=https://www.kura-select.com/articles/<slug>/`。**`--url=` には必ず絶対 URL を渡す**（Git Bash では `--url=/articles/...` のような `/` 始まりの値がパスに変換されて壊れる。メモリ `feedback_gitbash_regex_file_filter`）。先に同じコマンドの末尾に `--dry-run` を付けて送信先を確かめてもよい
   - **GSC の URL 検査で登録リクエスト**（ユーザー作業）をするよう伝える。済んだと言われたらログの「登録リクエスト」を日付に直す
4. 凍結台帳（JSON・メモリ）には書かない（測定しないため）

## 7. 提出前のセルフチェック

- [ ] スナップショットの確定日を書いたか（古ければその旨も）
- [ ] 凍結台帳を JSON とメモリの**両方**と突き合わせたか
- [ ] noindex・TODO の停止日・進行中の計画書の測定対象・14日以内の実施を外したか
- [ ] 禁止日を `grep -n "禁止日" docs/TODO.md` で全件見たか。月曜なら cron の注意を書いたか
- [ ] Bing の記事別を `bing_page_stats` から取ったか（スナップショットに記事別は無い）
- [ ] 提案は3件以内で、点数はカタログの値か
- [ ] T1 を選んだ記事で、実際のクエリを根拠に書いたか（推測のクエリで書いていないか）
- [ ] 今日 push してよい日かを書いたか
- [ ] 承認前に記事を編集していないか
- [ ] 実施した T1 の H2・FAQ が、全期間の疑問リストの項目に対応しているか
- [ ] 新しい事実の断定に収集ファイルの根拠があり、別のサブエージェントの照合を通したか

## 8. やらないこと

- 凍結を起こす・凍結台帳に記帳する（これは保守・加筆）
- title / description の改稿（主指標を決めた単独施策として別に計画する。CLAUDE.md §5.0.2）
- 商品構成の変更（追加・削除・差し替え）。必要なら kura-article-add か区分B/C の手順で別作業にする
- テンプレ・構造化データ・コンポーネントの変更（計画書→独立レビュー→実装。メモリ `feedback_review_before_implement`）
- カタログの型や点数をユーザーの承認なしに変える
- T10 の枠（`trend-topic` マーカーの範囲）を書き換える（`kura-trend-topics` が扱う）
- 効果の判定（このスキルは測定しない。数字の判定は kura-weekly-access-review）

## 9. 全面改稿モード

登録済みで集客の少ない記事1本を、`kura-index-recover` と同じ水準で作り直す。**1回の実行で1記事。** 型を足す通常のルーチン（§3〜§5）とは別の作業で、既存の本文の書き換えと商品説明の是正（区分C）まで行う。測定・凍結はしない。

### 9-0. 入力

- slug か URL を1つ。複数なら1本目だけ進め、残りは報告に書く。`article.id` への直し方は `kura-index-recover` §0 と同じ
- 「全面改稿の候補を出して」と頼まれたら、§1 の #6・#8 と §2 のふるい分けを通し、9-1 の条件に合う記事を**表示の多い順に最大3本**、根拠の数字つきで提案して止まる
- §0 の前提（カタログ・ログの有無、禁止日、月曜の cron）を同じように確かめる

### 9-1. 対象にしてよい記事

上から順に見て、最初に当たったもので止まる。止まったら根拠の数字と次の選択肢を書いて、ユーザーの判断を待つ。

| 順 | 条件 | 動き |
|---|---|---|
| 1 | `gsc_index_status` の `coverageState` が `Submitted and indexed` 以外 | **止まる。** 未登録なら `kura-index-recover` を案内する |
| 2 | §2 のふるい分けに当たる（凍結中・noindex・TODO で停止・進行中の計画書の測定対象・最終実施から14日以内・§2 の見送り・`draft: true`） | **止まる。** 理由と解禁日を書く |
| 3 | ログ §6 に同じ記事の行があり、+28日 が空 | **止まる。** 未登録の復帰の再確認を待つ |
| 4 | **集客が取れている記事**: 直近28日クリック ≥ 10、または直近週の表示/日 ≥ 10（CLAUDE.md §5.0.2 の R3 判定不能層の外） | **止まる。** 稼ぎ頭は順位が動いたときに失うものが大きい（メモリ `feedback_trend_topic_avoid_earning_articles`・`feedback_no_net_negative_changes`）。正しい商品是正でも表示・クリックが減った例がある（laundry-bleach・fabric-softener）。通常のルーチン（§3〜§5 の足すだけの型）を案内する |

- 順4 の数字は §1 #6 のスナップショットの確定日で切った GSC の28日（ページで絞る）と、直近7日の表示から出す。取り直したら確定日を報告に書く
- **ユーザーが「それでも全面改稿」と言えるのは順4 だけ。** そのときはリスク（上の例）を先に書き、ログに「R3 外だがユーザー判断で全面改稿」と残す。順1〜3 は上書きしない

### 9-2. 手順

`kura-index-recover` の §3〜§7 を、次の読み替えで使う。

| recover の節 | 全面改稿での扱い |
|---|---|
| §3 原因の仮説 | 「登録されない原因」ではなく**記事の弱点の診断**として、同じ4観点（兄弟記事との重なり・内部リンク・商品・本文）を根拠つきで書く |
| §4 疑問リスト | そのまま使う（GSC 全期間・Bing の `bing_page_query_stats`）。§3-2 の T10 との取り合いの除外も守る |
| §5 調べる | `../kura-article-create/references/article-research.md` の §1〜§2 に従い、サブエージェントに収集させる |
| §6 書く | そのまま使う。既存の本文は誤り・重複・定型文に限って書き換えてよい（理由はログに書く）。**title / description は事実の誤りの是正だけ**。商品の追加・削除・差し替えはしない（区分D。必要なら報告だけ）。`name` を変えるときの条件は recover §6「商品（区分C）」に従う |
