# KuraSelect 収益改善提案スキル

**このスキルの目的は「一般論のアフィリエイト改善策を排除すること」。** 検索すれば出てくる施策は、このサイトではすでに試して失敗しているか、規模的に効果を検出できないかのどちらかである。**提案の価値は、実測数値とこのサイト固有の失敗履歴に紐づいているかどうかだけで決まる。**

想定頻度は月1回〜四半期1回。週次の定点観測は `kura-weekly-access-review` の仕事なので、このスキルでは扱わない。

## 0. 前提の確認（ここを飛ばさない）

1. `reports/affiliate-performance-log.md` の週次ログに**直近4週以上**の行が埋まっているか確認する。3週以下ならブレが大きすぎて診断できないので、**その旨を述べてから進む**（止まらなくてよい）
2. `docs/ACCESS_ANALYSIS_*.md` の最新が2週間以上前なら、`pnpm weekly:snapshot` の実行をユーザーに促す
3. **数値は自分で MCP を叩き直さない。** 上の2ファイルに載っている確定済みの値を使う。載っていない切り口が必要なときだけ GA4/GSC MCP を使い、その場合は `CLAUDE.md` §5.0.2 の3ルール（確定日の実測・`dimensions: []`・確定日の明記）を守る
4. **失敗履歴をこの SKILL.md から読まない。** 後述 §2 の手順でその都度リポジトリから拾う（ハードコードすると陳腐化する）

## 1. 参照順（この順序を崩さない）

| # | 参照先 | 何を取るか |
|---|---|---|
| 1 | `reports/affiliate-performance-log.md` | 週次の管理画面クリック / 発生件数 / 報酬 / CVR / EPC。**直近8〜12週**を見る |
| 2 | `docs/ACCESS_ANALYSIS_*.md`（最新1〜2本） | GSC クリック・表示、GA4 の PV / セッション、送客イベント数、placement 内訳 |
| 3 | `docs/TODO_ARCHIVE_*.md` §0「失敗と決着の教訓」 | **過去に打った施策とその判定結果。失敗履歴の一次ソース。まずここを見る** |
| 3b | `docs/TODO.md` §3 カレンダー / §4 施策 / §6.5 | 未消化の予定と、まだアーカイブされていない直近の判定結果 |
| 4 | メモリ `project_measurement_holds` | 凍結中の記事と解除日。施策の中身と判定根拠 |
| 5 | `data/measurement-holds.json` | 凍結の機械可読一覧（4 と突き合わせる） |
| 6 | メモリ `project_high_ticket_asp_202608` / `project_adsense_202608` / `project_side_hustle_3tracks` | 楽天以外の収益トラックの現状と撤退判定日 |

2〜6 は、診断や提案に実際に使う範囲だけ読む。全文を読み込まない（トークン節約）。

## 2. 失敗履歴の収集（提案の前に必ずやる）

**まず `docs/TODO_ARCHIVE_*.md`（最新のもの）の §0「失敗と決着の教訓」を読む。** ここに失敗と結論が表で整理されている。
次に `docs/TODO.md` の §3 カレンダー・§4 施策・§6.5 で**アーカイブ後に出た判定**（✅/❌/△ が付いている行）を拾い、メモリ `project_measurement_holds` の判定済み行と突き合わせる。
こうして**「何を試して、どう失敗したか」のリストをその場で組み立てる**。

⚠️ **TODO.md は定期的に整理され、判定済みの行はアーカイブへ移る。** 「§3 に判定済み行が無い」ときは失敗が無いのではなく移動済みという意味なので、必ずアーカイブを開くこと。アーカイブが複数ある場合は最新1本＋直前1本を見る。

このリストは提案の採点基準になる。**提案する施策ごとに「このリストのどれとも重複しない理由」を1行で書けなければ、その施策は出さない。**

## 3. 診断（施策より先に必ずやる）

収益を4段に分解し、**どの段が落ちているか / 伸びしろがあるかを数字で特定する**。

| 段 | 定義 | 取り方 |
|---|---|---|
| ① 流入 | GSC クリック/日、GA4 PV | ACCESS_ANALYSIS §3 |
| ② 送客率 | GA4 のアフィリンククリック合計 ÷ PV | ACCESS_ANALYSIS §5 ÷ §3 |
| ③ 成約率 | 発生件数 ÷ **管理画面**クリック（CVR） | 成果ログ。GA4 クリックで割らない |
| ④ 単価 | 発生報酬 ÷ 管理画面クリック（EPC）、報酬 ÷ 発生件数 | 成果ログ |

**診断の作法**

- **単週で語らない。** CVR は 2.7〜13.9%、EPC は ¥6.6〜¥22.9 のレンジで週次に大きく振れる。**4週移動平均か中央値**で見て、単週の値はレンジ内かどうかだけ判定する
- **高単価1件への依存を必ず確認する。** 週報酬の大半が単一の高額成約であることが繰り返し起きている。平均と中央値が乖離していれば「その週は運」と書く
- 楽天 / Amazon / Yahoo を**分けて**見る。合算すると片方の異常が隠れる。Yahoo（バリューコマース）のクリックはクローラー混入の疑いがあるため成果予測に使わない
- **切り分けられないものは切り分けられないと書く。** 「クリック増・成約減」のような現象は、流入の質の変化と季節性・商品要因を単週のデータでは分離できない

## 4. 提案（3〜5件・期待インパクト順）

各施策について次の6点を必ず書く。**1つでも埋まらない施策は出さない。**

1. **具体的に何をするか** — 「コンテンツを充実させる」「導線を改善する」のような抽象語は禁止。対象記事名・変更箇所・作業内容まで書く
2. **なぜ効くか** — §3 の診断のどの段に効くのか、実測数値を引いて説明する
3. **失敗履歴との非重複** — §2 のリストのどれとも重複しない理由（1行）
4. **測定方法** — 指標 / 起点日 / 判定日 / 成功基準。凍結が必要なら解除日も
5. **検出可能性** — この規模（週クリック 200 前後、判定可能ページは全体の1割未満）で有意差を検出できるか。**できないなら「判定は諦めて打ちっぱなしにする」と明言する**。曖昧にしない
6. **作業量** — 週数時間の枠に収まるか。独自写真の撮影が必要なものはユーザー作業でブロックされる点を明記

**制約（提案が必ず満たすこと）**

- 凍結中の記事に施策を提案しない（`CLAUDE.md` §5.0.3 の区分B・区分Cは例外）
- 1記事1施策・1起点日。同一記事に複数施策を同時に提案しない
- 記事本文に価格・単価・年間コスト等の数値を書かせない（`CLAUDE.md` §5.0.1）
- 「最安」「No.1」等の断定表現、効果効能の記述を伴う提案をしない（`CLAUDE.md` §11）
- 有料被リンク・相互リンク集・自作サテライトは**着手禁止**（ガイドライン違反）
- **上位表示できている記事の商品構成を触る提案は原則しない**（2記事で2回とも順位を失っている）。出す場合は、なぜ今回は違うのかを §2 のリストを引いて説明する

## 5. やらないことの推奨（2〜3件）

一般には推奨されるが、このサイトの規模・制約では費用対効果が悪い施策を、理由付きで挙げる。**「やらない」を明示することがこのスキルの成果物の半分である。**

## 6. 前提の疑い

ユーザーの現状認識、過去の判定結果、このスキルの参照データ自体のうち、疑ってかかるべきものがあれば指摘する。**過去に「前提が誤りだった」ことが複数回ある**（比較表の単価欠落、StickyCta のデスクトップ仮説、AdSense の月1万PV前提）ので、遠慮しない。

## 7. 出力

- 出力先: `docs/REVENUE_REVIEW_<実行日>.md`（例 `REVENUE_REVIEW_2026-09-30.md`）
- 構成は `templates/report-template.md` の見出しを**そのまま**使う。見出しを足さない・減らさない・並べ替えない
- ChatGPT 等の外部AIにセカンドオピニオンを求めたいと言われたら、`templates/standalone-prompt.md` の `{{ }}` を**その時点の実測値と §2 で集めた失敗履歴で埋めて**出力する（テンプレをそのまま渡さない）

## 8. 提出前のセルフチェック（全項目を満たすまで出さない）

- [ ] 診断（§3）を施策より先に書いたか。4段のどこがボトルネックか数字で示したか
- [ ] 単週ではなく4週移動平均か中央値で語ったか。高単価1件への依存を確認したか
- [ ] CVR を**管理画面**クリックで割ったか（GA4 クリックで割っていないか）
- [ ] 楽天 / Amazon / Yahoo を分けたか
- [ ] 施策ごとに §4 の6点すべてを書いたか
- [ ] 施策ごとに §2 の失敗履歴との非重複を書いたか
- [ ] 検出可能性について「できない」場合に、はっきり「判定を諦める」と書いたか
- [ ] 凍結中の記事に施策を提案していないか（JSON とメモリの**両方**と突き合わせたか）
- [ ] 提案は5件以内か。優先順位を付けたか
- [ ] 「やらないことの推奨」を書いたか
- [ ] 根拠のない数値予測（「30%改善します」等）を書いていないか
- [ ] 施策を提案した場合、台帳2箇所への追記（起点日・解除日・指標。JSON の `releaseDate` は解除日の翌日）を宿題として明記したか

## 9. やらないこと

- 記事ファイル・データファイルの編集（このスキルは読んで提案するだけ。実施は承認後に別作業）
- 一般的なアフィリエイト/SEO ベストプラクティスの列挙
- 10件以上の施策の羅列。優先順位のない提案
- 週次の定点観測の代替（それは `kura-weekly-access-review`）
