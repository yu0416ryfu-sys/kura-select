# KuraSelect 話題の追従（T10）

**このスキルの目的は、SNS・世間で話題になっている事柄を、投稿を貼らずに「読者の疑問への答え」として記事に反映し、世間の動向に合った情報を出すこと。** 古くなった話題を残さないことを、新しい話題を入れることより優先する。

流れは **期限切れの処理 → 話題を集める（外の情報源で拾う → 受け皿の記事に結び付ける → X・Yahoo!リアルタイム検索で話題か確かめる）→ ふるい分け（§4）→ GSC で裏付け（§3。ページの表示と話題のクエリ）→ トレンドで伸びを見る（A に当たらなかった候補のうち、B ① を満たすか種類 (a)〜(c) のものだけ。B（事実）に決まった候補を除く。データ不足なら Yahoo!リアルタイム検索の推移）→ 提案して止まる → 承認分だけ実施 → 記録**。提案のあと、ユーザーの判断を待たずに記事を編集しない。

計画書: `docs/IMPLEMENTATION_PLAN_TREND_TOPICS_2026-10-25.md`（第7版）・`docs/IMPLEMENTATION_PLAN_TREND_TOPICS_2026-10-27_V9.md`（第9版。案1 Yahoo!リアルタイム検索の推移・案2 B（事実）・案3 GSC＋Bing・⑥⑦ の情報源。2026-10-27 から4週の試行中）。型の定義（書き方・禁止）は `docs/CONTENT_IMPROVEMENT_CATALOG.md` の T10。

## 運用の決まり（2026-10-25 ユーザー決定）

- 話題には**日付を書く**。**3か月で期限切れ**にし、時期を問わない書き方に直すか削除する
- **1記事1枠**。新しい話題は古い枠と**差し替え**る（積み上げない）
- **週1回**、人間が実行する（`docs/TODO.md` §8 継続ルーチン: 毎週月曜・週次分析の後）
- **数値を書かない**（価格・単価・割合・順位・件数。CLAUDE.md §5.0.1）
- ログは `docs/CONTENT_IMPROVEMENT_LOG.md` に**一本化**する（§1 実施ログ・§3 有効中の話題枠・§4 新規記事の種）
- 採用する話題は **下の「採用の段階」の3段階に分ける**。GSC は A の判定（話題のクエリ）と B の「記事に読者がいるか」（ページの表示）に使い、**話題そのものの需要は X とトレンドで見る**
- 話題は先に**外の情報源**（§2 の順1）から拾い、受け皿の記事に結び付ける
- 一次情報リンクを単独の施策として足すことはしない。T10 の中で根拠が要るときだけ公式の出典を1つ添える
- X は**ユーザーがログイン済みの Chrome を Claude in Chrome で読むだけ**（1回5検索まで・投稿/いいね/リポスト/フォロー/DM/設定変更をしない）。Yahoo!リアルタイム検索・Google トレンドは補助。本数を増やしても X の検索回数は据え置き、足りない分は Yahoo!リアルタイム検索で補う。Google トレンドも Claude in Chrome で開く（内蔵ブラウザは 429 になった）

### 上限（1回の実行あたり）

- **新規・差し替えは合計5本まで**。そのうち段階B は2本まで、段階C は1本まで
- **期限切れ（§1 の 1〜5）と見直し期限（§1 の 6）の処理は上限の外**（後始末で新しい枠を減らさない）。上限の外になるのは「一般化・削除・A への昇格・見直し期限の延長」まで。**同じ記事に新しい話題を入れるなら、それは通常の新規として上限と段階の条件に数える**（その記事の14日ルールだけは、直前の後始末を実施に数えない）
- 上限の外の処理も**1回あたり5本まで**。期限・見直し期限の古い順に処理し、残りは次回に回す（実行が止まった週のたまり分を一度に出さない）
- **条件を通った話題が上限に満たなければ、そこで止める。** 本数を埋めるために条件を緩めない
- **同じ話題は1回の実行で1記事まで**。複数の記事が受け皿になるときは、**段階が上の記事 → 同じ段階ならページの28日のクリックが少ない記事（同数なら表示が少ない記事）**の順で選ぶ。すでに集客が取れている記事は、加筆で順位が動いたときに失うものが大きいので避ける（2026-10-25 ユーザー決定。B の受け皿はページの表示100以上が前提なので、読者のいない記事は選ばれない）
- **ログ §3 に同じ話題の有効な枠があれば、別の記事には入れない**（週をまたいで同じ話題を広げない）。その枠が期限切れ・削除・一般化で消えた後は、通常の候補として扱う
- 「同じ話題」は、候補の話題の言葉（表記ゆれ）と、ログ §3 の「話題の言葉（表記ゆれ）」が**1語でも重なる**こと（1回の実行の中の候補どうしも同じ基準）
- **話題の言葉（表記ゆれ）には、下の「測る語」で定義する一般語・ジャンル語だけの語を入れない**（例「値上げ」「高い」「マスク」を単独で入れない。「ピジョン 値上げ」「インフルエンザ」のように話題を指す語だけを書く）。一般語が重なって関係の無い記事の話題まで止まるのを防ぐ

### 採用の段階

GSC・Bing は §3 の取り方。「話題のクエリの表示」は話題の言葉を含むクエリの、対象記事のページでの直近28日の **GSC と Bing の合計**。「ページの表示」は対象記事のページ全体の直近28日の表示（**GSC だけ**。Bing は足さない）。

| 段階 | 採用の条件 | 枠の扱い |
|---|---|---|
| **A（確度高）** | 話題のクエリの表示（**GSC＋Bing の合計**）が **3以上** | 期限は入れた日＋3か月 |
| **B（先回り）** | 次の3つを**すべて**満たす: ① **ページの表示が100以上**（記事に読者がいる。GSC だけ）② X で話題になっている ③ Google トレンドで**伸び**。**話題のクエリの表示は問わない**（0〜2でよい）。話題の種類は (a)〜(d) のどれでもよい（種類の決まりはかかる）。**B（事実）**: 下の注記 | 期限3か月に加え、**見直し期限＝入れた日＋4週** |
| **C（読者が困る事実）** | ページの表示・話題のクエリの表示を問わず、次の2つを**すべて**満たす: ① 話題の種類が **(a)〜(c)** のどれか（(d) は C にしない） ② X で話題になっており、かつ Google トレンドで伸び。一次情報は種類の決まりで必須 | B と同じ（見直し期限＝入れた日＋4週） |

**B（事実）**（第9版 案2）: 種類が **(a) または (c)** で、**一次情報（メーカー・公的機関の発表の URL）を開いて中身を確かめた**ものは、B の ③（トレンドで伸び）を問わず、① ページの表示100以上 と ② X で話題 の2つで B にする。
- (b)・(d) には使わない
- 一次情報は**中身まで**確かめる（例: 価格改定のお知らせなら、対象商品の一覧の PDF で、その記事のジャンルの商品が入っていること）。一覧ページの見出しだけでは B（事実）にしない。開けなかったら次回に回す
- **B（事実）に当たる候補ではトレンドを測らない**。GSC の後、A に当たらず、種類 (a)(c)・① ページの表示100以上・② X で話題・一次情報の中身を確かめた、の4つがそろった候補は、その時点で B（事実）に決める。一次情報の中身をその回に確かめられなかった候補は、トレンドを測らずに次回に回す（通常の B に切り替えて測らない）
- 段階としては **B のまま**: 上限（B 2本）・見直し期限（入れた日＋4週）・B 停止の集計（§0 の 5）・書き方の決まりは B と同じ。**マーカーの `tier=` もログ §3 の段階の列も `B`**（「（事実）」は段階の値に入れない）。B（事実）であることはログ §3 の「裏付け」の列の先頭に `B（事実）:` と書いて示し、ログ §1 の内容には「段階B（事実）」と書く（§8）
- 見直しのために、**採用時に Yahoo!リアルタイム検索の推移の語を決めて記録する**: 「測る語」の ① 話題＋ジャンル語 →（① で30日が0件なら）② 話題だけの語 の順で選び、§2 の順2 でメモした件数（メモが無ければその回に開く・10回の内数）を、ログ §3 の「トレンドで測った語」に `Yahoo推移: <語>（7日 N / 30日 M）・B（事実）` と書く
- **B（事実）の別集計と停止**は §0 の 6。**B（事実）停止中**は、(a)(c) の候補も通常の B としてトレンドを測る（データ不足なら案1）。B 停止中（§0 の 5）は B（事実）も B なので出さない

段階の決め方: **上から順に当てはめ、最初に当たった段階にする**（A と B の両方に当たれば A、B と C の両方に当たれば B）。段階は根拠の強さだけで決め、書き方の縛りは次の「話題の種類」で決める。上から順なので、C に入るのは実際には B ①（ページの表示100以上）を満たさない記事の (a)〜(c) の話題になる。

- 「X で話題」は、Claude in Chrome で X を見たときに加え、**Yahoo!リアルタイム検索に出た X の投稿でも満たす**（どちらも投稿が複数あり、ここ1〜2週に集中していること）
- 「Google トレンドで伸び」は、日本・過去90日で直近の値が期間の前半より高いこと（季節の語は過去5年で前年同期と比べる。下の「測る語」）。**トレンドが「データ不足」なら伸びではない**（① ② ともデータ不足なら、季節の語を除き、案1 の Yahoo!リアルタイム検索の推移で判定する。案1 の推移もデータ不足（30日・7日が0件）なら伸びではない。B（事実）はトレンドを問わない）。「横ばい以上」（見直しの延長）の定義は、下の「見直し期限の判定」の 2 の「話題が続いている」に書いたもの（季節の語は前年同期と比べる）
- 段階A・B の候補が出た記事に C の枠があれば、A・B を優先して差し替える（14日ルールは通常どおり）

### 話題の種類

**種類の決まりは段階 A・B・C のどれで入れても同じようにかける。**

| 種類 | 中身 | 段階に関係なくかける決まり |
|---|---|---|
| **(a) 製品の事実** | 仕様変更・販売終了・品薄・リコール・成分や規格の変更など | メーカー・公的機関の**一次情報が必須** |
| **(b) 公的機関の注意喚起** | 感染症の流行・熱中症・乾燥・大雪など、その記事の商品を買う・使う判断に関わるもの（例: インフルエンザの流行の注意 → マスク・ハンドソープ） | 公的機関の**一次情報が必須**。商品の効果は書かず、公的機関が勧めていることを伝聞で伝え、商品選びの観点に絞る。「ウイルス」「感染対策」「予防」「防ぐ」を商品と結び付けて書かない（マスクは雑貨で、薬機法・景表法にかかるおそれ）（§7 の禁止） |
| **(c) メーカー公式の価格改定・容量変更・パッケージ変更の発表** | メーカーのニュースリリース・お知らせ | メーカーの**一次情報が必須**。「メーカーが価格改定を発表した」ことに限って書き、**販売価格が上がると言い切らない**（多くは出荷価格の改定で、楽天での販売価格とは限らない）。改定の時期（「11月から」など）は書いてよい。改定率・価格は書かず「ページ上部の比較表（自動更新）でご確認ください」で誘導する。買い急ぎを勧めない。容量変更は記事の `products[]` の `capacity` / `pricePerUnit` と合っているかを確かめる（§7）（§7 の禁止） |
| **(d) その他の話題** | SNS で話題の使い方・疑問・感想など、(a)〜(c) に当たらないもの | 段階 A・B だけで入れる（C にしない）。雑談的な流行は使わない。伝聞で書く |

### 「Google トレンドで伸び」の測る語

- 測る語は**話題を表す語**。次の順に試す: ① 話題の言葉＋ジャンル語（例「トイレットペーパー 値上げ」）② 話題だけを表す語（例「インフルエンザ」、社名＋出来事の「ピジョン 値上げ」）
- **① が「データ不足」なら ② に進む。** ① にデータがあって「伸びでない」なら、**② に進まずそこで止める**（伸びる語を探して選ばない）。② も「データ不足」なら伸びではない
- **「データ不足」の線引き**: Google トレンドが「データ不足」と表示したとき、または過去90日の**3分の2以上の点が0**のとき（初回記録の「ほぼ0で単発の山」はこちら）
- **ジャンル語だけ**（「トイレットペーパー」「マスク」）や、**一般語**では判定しない。一般語＝**ジャンル（商品の種類）も出来事（いつ・誰が・何をしたか）も指さない語**（例「値上げ」「高い」「値段」）。ジャンルの需要や世の中全体の動きで、その話題の伸びではないため
- **季節の語**（感染症・乾燥・熱中症・大雪・花粉など、毎年同じ時期に山が来る語）は、過去90日の前半との比較では季節だけで伸びに見える。**過去5年の表示に切り替え、直近の値が前年の同じ時期より高いとき**だけ伸びとする（この確認も1語に数える）
- **1語ずつ開く**（複数語を1画面で比べない）。1回の実行で開くのは、見直し期限の再測定・新規の候補・§6 の種の確認を**合わせて10語まで**。この順で使い、足りない分は次回に回す
- 測った語はログ §3 の「トレンドで測った語」に書く（見直しで同じ語を測り直すため）

#### ① ② ともデータ不足のとき: Yahoo!リアルタイム検索の推移（第9版 案1）

- 使う場面: ① も ② も「データ不足」になったときだけ
- **使わない場面**: トレンドにデータがあって「伸びでない」とき（そこで止める。物差しを選び直して伸びを探さない）／**季節の語**（30日では前年同期と比べられないため）／Google トレンドを 429・CAPTCHA・ボット判定で止めた回（§2 の順4。データ不足かどうかが分からないので案1 にも進めない）
- 測る語: トレンドで「データ不足」だった **① の語**をそのまま Yahoo!リアルタイム検索で開く。① の語で30日が0件なら ② の語を開く（この2回で打ち切る）。開いた回は Yahoo!リアルタイム検索の10回に数える
- **件数は §2 の順2 の検索のときに先にメモしておく**（§2 の順2）。後でトレンドがデータ不足になったら同じ語のメモを使う（開き直さない・回数を増やさない）。メモの無い語だけを新しく開く
- 読み方: 「ポスト数グラフ」の **7日** と **30日** のタブを手でクリックし、「N件のポスト」の数を読むだけ（グラフの点を一つずつ読まない・スクリプトで読まない）。タブを押してもすぐには数字が変わらないことがあるので、**グラフの下の日付の目盛りが押したタブの期間に変わったのを確かめてから読む**
- **伸び**: 7日の件数が **10件以上** かつ **30日の件数の3分の1以上**（両方）
- **横ばい以上**（見直し期限の判定2 の「話題が続いている」）: 7日の件数が **5件以上** かつ **30日の件数の5分の1以上**
- 30日が0件・7日が0件なら、データ不足（伸びではない）
- 記録: ログ §3 の「トレンドで測った語」に `Yahoo推移: <語>（7日 N / 30日 M）` と書く（Google トレンドでデータ不足だった語も並べて書く）。見直しのときはこの語を同じ物差しで測り直す（Google トレンドに戻さない）。件数はログにだけ書き、本文には書かない

### 見直し期限の判定（B・C 共通）

**スナップショットの確定日が見直し期限以降**になってから行う（窓は確定日までの28日なので、枠を入れる前の日が混ざらない）。枠を入れた後なら記事が話題に答えているので、**話題のクエリの表示はここで検証する**（B の採用条件から外した分を、ここで確かめる）。ただし少ない表示のクエリは匿名化で落ちるので、**表示だけで消さず、話題が続いているかも見る**。上から順に当てはめて最初に当たったものに決める（表示はすべて、ログ §3 の「話題の言葉（表記ゆれ）」を含むクエリの **GSC＋Bing の合計**の表示。取り方は §3）:

1. 28日で **3表示以上** → **A に上げる**（`review=`・`extended=` を消し `tier=A`。期限は入れた日＋3か月のまま）
2. まだ延長していなくて、次のどちらかに当たる → **見直し期限を4週延ばす**（`extended=1`。**段階は変えない**。1回だけ。**延長後の見直し期限＝旧見直し期限＋28日**。判定が遅れても判定日から数えない）
   - 28日で **1〜2表示**
   - **話題が続いている**: ログ §3 の「トレンドで測った語」を同じ決まりで測り直して**横ばい以上**（過去90日で直近の値が期間の前半と同じくらいか高い。季節の語は過去5年で直近の値が前年の同じ時期と同じくらいか高い。データ不足は続いていない扱い。ただし Google トレンドを止めた回は §2 の順4 の保留に従う（未延長・0表示の枠は次回へ））、かつ X か Yahoo!リアルタイム検索で**直近2週に投稿が複数**ある。**「トレンドで測った語」が `Yahoo推移:` の枠**（案1・B（事実））は、その語を Yahoo!リアルタイム検索の推移で測り直して「横ばい以上」（7日5件以上かつ30日の5分の1以上）かを見る（語を選び直さない・Google トレンドに戻さない）
3. それ以外（延長済みで2表示以下、または表示0で話題も続いていない）→ **一般化するか削除する**（時期を問わない内容として読者に役立つなら一般化。§1 の 3 と同じ扱いで、一般化したら §3 の行を消し §1 に記録）

## 3. GSC で裏付ける

- **GSC の役割**: A の判定（話題のクエリ）と、B の「記事に読者がいるか」（ページの表示）。**話題そのものの需要は GSC では測らない**（書く前は話題のクエリが立たない・少ない表示のクエリは匿名化で落ちる・確定日より後の話題は窓に入らない）。話題のクエリが立つかは、枠を入れた後の見直し期限（§1 の 6）で確かめる
- **§4 のふるい分けを先に行い**、条件に当たらなかった候補の記事（**最大8本**＋見直し期限の記事。段階は GSC の後に決まるので、上限の5本より多めに取る）ごとに、直近28日（**終端はスナップショットの確定日**。確定日を叩き直さない）で次の2つを `gsc_search_analytics`（MCP `mcp__gsc__gsc_search_analytics`）で取る:
  1. **ページの表示**: `dimensions: []`・`filterPage: https://www.kura-select.com/articles/<slug>/` で取る（**合計は `[]` で取る。query 行を足し上げない**。CLAUDE.md §5.0.2 のルール3）。B ① の判定に使う。同じ行のクリックは、同じ話題の受け皿が複数あるときの選び方（上限の「同じ話題は1回の実行で1記事まで」）に使う
  2. **話題のクエリの表示**: `dimensions:["query"]`・同じ `filterPage`・`rowLimit: 5000` で取り、話題の言葉を含むクエリを探す（`kura-content-improve` §3-2 の T1 と同じ取り方）。A の判定に使う
  3. **Bing の話題のクエリの表示**（第9版 案3）: `bing_page_query_stats`（MCP `mcp__bing__bing_page_query_stats`）に `page: https://www.kura-select.com/articles/<slug>/`・`startDate: 確定日−27日`・`endDate: 確定日`（GSC と同じ窓）・`sortBy: "Impressions"`・`rowLimit: 1000` を渡し、話題の言葉（表記ゆれ）を含むクエリの `Impressions` を合計する。**2 と足した合計**を「話題のクエリの表示」とする（閾値3は変えない）
     - 行は週単位で、窓の終わりの1〜2週は反映前のことが多い。**欠けている週を補わない**（あるだけを足す）
     - **`Date` が窓の中にある週だけを足す**（窓の端にかかる週を按分しない・窓の外の `Date` の週を足さない。MCP に `startDate`・`endDate` を渡せばこのとおりになる）
     - 返った行数が `rowLimit` と同じなら打ち切りの可能性があると提案に書き、閾値近くの話題は採用しない
     - **B ① のページの表示には Bing を足さない**（GSC のまま）
- サイト全体を `["query","page"]` で1回取る方法は使わない（5000 行で打ち切られ、少ない表示の行から落ちるため）
- 返ってきた行が 5000 ちょうどなら打ち切りの可能性があると提案に書き、閾値近くの話題は採用しない
- **トレンドは GSC の後に測る**。GSC で A に当たった候補と、B ①（ページの表示100以上）を満たさない種類 (d) の候補にはトレンドの語を使わない。**B（事実）に決まった候補・一次情報の確認を次回に回した (a)(c) の候補は測らない**（B（事実）停止中（§0 の 6）はこの除外を当てはめず、(a)(c) も通常の B として測る）。測る順は、見直し期限の再測定 → 通常の B の候補（ページの表示が多い順）→ B ① を満たさない (a)〜(c) の候補 → §6 の種
- 段階の決め方: 話題のクエリの表示（GSC＋Bing。表記ゆれは候補ごとに列挙して合算）が3以上なら A。届かなければ、種類 (a)(c)・ページの表示100以上・X で話題・一次情報の中身を確かめた、がそろえば **B（事実）**（トレンドを測らない）。次に通常の B の条件（ページの表示100以上・X・トレンド。① ② ともデータ不足なら案1 の推移）、次に C の条件（種類 (a)〜(c)・X とトレンド。データ不足なら案1）を確かめる（「採用の段階」の「上から順に」）。段階と別に**話題の種類 (a)〜(d) を決め、(a)〜(c) なら一次情報を確かめる**（段階 A・B でも）
- 列挙した表記ゆれは、採用したらログ §3 の「話題の言葉（表記ゆれ）」に書く
- 段階のどれにも当たらない話題は T10 に使わない。既存記事に受け皿が無いジャンルの話題は §6 の種に回す

## 4. ふるい分け（候補から外す記事）

`kura-content-improve` §2 と同じ条件で外す。外した理由はまとめて1行で書けばよい。

- 凍結中（対照群を含む）。`data/measurement-holds.json` の `releaseDate > 今日` の行の slug と、メモリ `project_measurement_holds` の**両方**を見る
- noindex 中（`data/noindex-articles.json`）
- `docs/TODO.md` §3 で日付つきで止められている（その日付を書いて次回以降に送る）
- `docs/TODO.md` §3 で進行中の計画書の測定対象（前窓・後窓）に入っている記事。後窓の終わりが未確定なら「後窓未確定」と書いて外す
- **14日以内に実施した記事**（ログ §1。T10 を含むすべての型。ただし直前の T10 の後始末（一般化・削除・昇格・延長）だけの行と、型 `T10集計` の行は数えない。`kura-content-improve` 側は後始末の行も数える）
- 実施ログ §2 で見送られ、理由がまだ解消していない記事×型
- `draft: true` の記事

加えて、次の話題は使わない:

- 炎上・事故・リコールの話題で一次情報が見つからないもの
- 効能の主張が中心の話題（例:「〇〇で肌荒れが治った」）
- 記事のテーマ（title が答えている問い）から外れる話題

⑥⑦ で拾った話題には、さらに次の3つをかける（第9版）:

- **ランキングに出ているだけの話題は使わない**: ⑦ で拾った話題は、Yahoo!リアルタイム検索・X で直近2週に投稿が複数あるか、⑥ やメーカーの発表があることも確かめる（⑦ だけでは使わない）
- **セールで上がっただけの話題は使わない**: 商品名にお買い物マラソン・スーパーSALE・クーポン・期間限定の値引きがあり、ほかに話題の手がかりが無いもの
- **宣伝の持ち込みは使わない**: PR TIMES の発表は「発表があった」事実の根拠にだけ使い、商品の良し悪しの根拠にしない

## 5. 提案して止まる

チャットに次の形で出す。ファイルは作らない。

```

前提: スナップショット確定日 YYYY-MM-DD ／ 今日の push: 可・不可（理由）／ B: 継続・停止中（集計日）／ B（事実）: 継続・停止中（日付）
回数: 外の情報源 N/12 ページ ／ Yahoo!リアルタイム検索 N/10 回 ／ X N/5 回（ログイン切れなら「飛ばした」）／ トレンド N/10 語
マーカーとログ §3 の突き合わせ: ずれなし（あれば内容）

### 新規・差し替え（最大5件・B は2件・C は1件まで）

| # | 記事 | 話題 | 拾った情報源 | 段階（A/B/C） | 話題の種類（a〜d） | 話題の言葉（表記ゆれ） | 裏付け（A: 話題のクエリ GSC N・Bing M/28日、B: ページの表示/28日（B（事実）は先頭に `B（事実）:`）、C: 一次情報） | X/トレンドで見たこと（要約・トレンドで測った語） | 新規 or 差し替え | 書く内容（見出し案） | 注意 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | ... | ... | ③ 厚労省 | B | (b) | インフルエンザ / インフル | ページ 1,486 表示・一次情報 URL | X で ここ1週に複数・「インフルエンザ」過去5年で前年同期より高い | 新規 | ## 〇〇が話題ですが、△△は気にした方がいい？（2026年10月時点） | 効果を書かない・数値は比較表へ誘導 |

### 期限切れ・見直しの処理（件数に数えない・最大5件）

| # | 記事 | 話題 | 期限切れ処理 or 見直し | 判定（一般化・削除・A へ昇格・延長） | 根拠（話題のクエリの表示/28日・トレンドで測った語の向き・X/Yahoo!リアルタイム検索の直近2週） |
|---|---|---|---|---|---|

候補から外した記事: 凍結中 N本、14日以内に実施 N本、TODO で停止中 N本、テーマ外の話題 N件、同じ話題（ログ §3 に有効な枠あり・同じ回で別記事を選んだ）N件
新規記事の種（§6）: 追記 N件・判断を埋めた種 N件
```

- 「拾った情報源」は §2 の順1 のどれか（①〜⑦）、または記事のジャンル語
- 段階の列は A/B/C のまま。B（事実）は裏付けの列の先頭に `B（事実）:` と書く。案1 を使ったら「X/トレンドで見たこと」に `Yahoo推移: <語>（7日 N / 30日 M）` を書く
- 試行中（第9版の実装後の最初の4回）は、提案のあとにログ §5「T10 試行メモ（第9版）」に1行書く（提案を出さなかった回も書く）
- **新規・差し替えは5件まで（B は2件・C は1件まで）。** 期限切れ・見直しの処理は件数に数えず、別の表にまとめる。B 停止中なら B を出さない
- 割合・件数・価格などの数値が見出し案・本文案に入っていないかを提案の時点で確かめる（本文 lint は円表記しか止めない）
- 点数はカタログの値（6.5）を使う。記事ごとに点数を作り直さない
- 出したら止まり、ユーザーの判断（どれをやるか・見送るか）を待つ

## 6. 新規記事の種（③）

- 既存記事に受け皿が無いジャンルの話題は、ログ §4 に「確認待ち」で記録する（初めて見た日・話題（ジャンル語）・情報源）
- 「既存記事に受け皿が無い」は page 単位ではなく、**サイト全体の query 次元**（`kura-article-recommend` の採択基準と同じ測り方）で判断する
- **初めて見た日から14日以上**たった種について、実行のたびに次の3点を確かめて「2週後の確認日」「需要の向き」「楽天で同用途5件以上」「判断」を埋める:
  1. Google トレンドで需要が**伸び・横ばい**（下降なら見送り）。測り方は「測る語」の決まり（1語ずつ・データ不足の線引き・季節の語は前年同期）で、語数は1回10語の上限に含める（見直し・新規の後に使い、足りなければ次回）
  2. ジャンル語が**一般名詞**（固有の商品名・流行語は見送り）
  3. 楽天で**同じ用途・同じ年齢層**の商品が5件以上（メモリ `feedback_no_mixed_use_rankings`）
- 3点を満たした種は「kura-article-recommend へ回す」、満たさなければ「見送り（理由）」とする
- 回した種も、recommend の基準（サイト全体の query 次元で、テーマ語＋選択系語のクエリが28日で表示30以上）を通らなければ見送りになる。**受け皿の無い話題は表示が立たず、見送りになるのが普通。** 種は「需要が育ったジャンルを見逃さないための記録」であって、候補を増やす仕組みではない

## 7. 承認された分だけ実施する

`kura-content-improve` §5 の 1〜6 に従う:

1. **1記事1コミット。** 編集の前に記事を Read する（CLAUDE.md §13）
2. カタログ T10 の「書き方」「禁止」に従う（下にも要点を書く）。既存の本文・見出しは書き換えない（差し替え・期限切れの処理で触るのは `trend-topic` マーカーの範囲だけ）
3. 凍結中の記事を Edit しようとして hook（`freeze-guard`）が止めたら、作業を止めてユーザーに伝える（ふるい分けの漏れ）
4. `pnpm test` と `pnpm build` を通す（本文 lint・Zod・OGP）。出力が長いのでサブエージェントに任せてよい（メモリ `feedback_token_saving_subagents`）。計画書5 Part A（`data/content-dates.json`）が main に入っていて `pnpm test` が落ちたら `pnpm content:stamp` を実行し、更新された台帳を同じコミットに入れる
5. コミットメッセージは日本語で、「<slug> に <話題> の H2 を加筆」「<slug> の話題枠を <新しい話題> に差し替え」の形にする（期限切れ・見直しは「<slug> の話題枠を一般化」「<slug> の話題枠を削除」など）
6. push はユーザーの指示があってから。禁止日は避ける

- 種類 (c) の容量変更の話題では、記事の `products[]` の `capacity` / `pricePerUnit` が新しい容量と合っているかを確かめる。ずれていても**手で直さず**提案に書く（自動更新のデータ欄。CLAUDE.md §5.0.3 区分A・メモリ `feedback_md_update_policy`）

### 書き方の要点（カタログ T10）

- 位置は、見出しが**ちょうど `## まとめ`**（`^## まとめ$` の完全一致。「## まとめ買いの〜」は当たらない）の H2 の直前。完全一致の見出しが無い記事（2026-10-25 時点で rakuten-marathon-guide・water-server-comparison・water-server-delivery-comparison・reviews/shampoo-pantene-damage-care-review の4本）は、本文の最後の H2 の節の後。確かめるコマンド:
  ```bash
  grep -n -E "^## まとめ$" src/content/articles/<slug>.md
  ```
- 見出しは `## <話題の言葉を含む疑問>（YYYY年M月時点）`。見出しの直後の1〜2文で答えを先に書く
- 枠の前後をマーカーで囲む:
  ```markdown
  <!-- trend-topic:start tier=B added=2026-10-25 review=2026-11-22 expires=2027-01-25 -->
  ## 〇〇が話題ですが、△△は気にした方がいい？（2026年10月時点）

  答えを先に1〜2文。……
  <!-- trend-topic:end -->
  ```
- `tier` は A / B / C。`review` は B・C のときだけ書く（初回は入れた日＋28日）。延長したら `extended=1` を足し `review` を旧見直し期限＋28日にする（段階は変えない）。A に上げたら `review=` と `extended=` を消し `tier=A` に直す。`expires` は入れた日の3か月後の同日。**ログ §3 と同じ値にする**
- SNS の内容は「〜という声が見られます」「〜が話題になっています」の伝聞で書き、投稿の文章を引用しない。投稿者名・ID を書かない
- 根拠が要る断定（リコール・仕様変更・販売終了など）は、メーカー・公的機関の一次情報を本文に1つだけ示す（通常の外部リンク。ウィジェット不可）
- 数値が要る話題（値上げ・品薄など）は「ページ上部の比較表（自動更新）でご確認ください」で誘導する
- 本文の太字は、閉じる `**` の直前が約物なら `<strong>` で書く（メモリ `feedback_markdown_bold_cjk`）

### 禁止（カタログ T10）

- 価格・単価・割合（「〇%値上げ」）・順位・件数・レビュー数を書く（本文 lint は円表記しか止めないので、割合・件数は人が確認する）
- 効果効能の断定、噂の断定、特定商品・メーカーへの否定の断定（薬機法・CLAUDE.md §11）
- 炎上・事故・リコールの話題を一次情報なしで書く（種類 (a)〜(c) は段階に関係なく一次情報が必須）
- 種類 (a)〜(c) の話題を、段階に関係なく一次情報なしで書く
- 公的機関の注意喚起（種類 (b)）で、商品の効果を書く（「予防できる」「防げる」など）。「ウイルス」「感染対策」「予防」「防ぐ」を商品と結び付けて書く。書くのは公的機関が勧めていることの伝聞と、商品選びの観点だけ
- 価格改定の話題（種類 (c)）で、改定率・価格を書く、販売価格が上がると言い切る（書くのは「メーカーが価格改定を発表した」ことまで）、買い急ぎ・買いだめを勧める（「値上げ前に買っておきましょう」など）
- FAQ（frontmatter `faqs[]`）に話題を入れる（FAQPage の構造化データに日付つきの話題が残るため）
- 売れ行きを書く（「売れている」「人気No.1」「ランキング1位」「完売続出」。順位は数値でもある）。書けるのは「話題になっています」まで。比較表に無い商品の名前は一次情報に出ているときだけ書き、楽天のリンクを付けない（比較表を変えるのは区分D で、T10 ではしない）
- 1記事に2枠以上置く
- 凍結中・noindex・`draft: true` の記事に入れる

### 初回適用時の確認

T10 を初めて記事に入れるときは、凍結していない記事で行い、`pnpm build` 後に `dist/articles/<slug>/index.html` で次を確かめる:

- 話題の H2 が本文と目次（`ArticleToc`）に出ること
- **表示される本文のテキスト**（タグとコメントを除いた文字列）に `trend-topic` が含まれないこと（HTML のソースにコメントの日付が残るのは許容する）
- 本文 lint・ビルドが通ること

## 8. 記録する

実施したら、同じ作業の中で:

1. `docs/CONTENT_IMPROVEMENT_LOG.md` §1 の**先頭**に1行足す（日付・slug・型 `T10`・内容・コミット・登録リクエスト＝「未」）。「内容」は、**先頭にラベル**を付け、続けて段階・種類・話題の言葉（表記ゆれ）を書く（§0 の 5 の集計と `kura-content-improve` の T1 の除外に使う）。ラベルは次の8種のどれか1つ:
   - `新規` / `差し替え` / `見直し→A` / `見直し→延長` / `見直し→一般化` / `見直し→削除` / `期限切れ→一般化` / `期限切れ→削除`
   - 例「見直し→削除: 段階B・種類(d)・話題の言葉 インフルエンザ / インフル」
   - B（事実）の枠は、新規・差し替えの行**とその枠の見直しの行すべて**に「段階B（事実）」と書く（§0 の 6 の別集計に使う。§1 はマーカーと照合しないので「（事実）」を書いてよい）。例「見直し→削除: 段階B（事実）・種類(c)・話題の言葉 ライオン 値上げ / 猫砂 値上げ」
2. §3 を追加・書き換え・削除する（差し替えは行を書き換え、期限切れ・見直しで削除・一般化したら行を消す。昇格・延長は段階・見直し期限・延長済みを直す）。**「話題の種類」「話題の言葉（表記ゆれ）」「トレンドで測った語」（B・C）を必ず埋める**。「裏付け」は A なら話題のクエリの28日の表示を `話題のクエリ GSC N・Bing M（28日）` と内訳で、B ならページの28日の表示、C は `—` とし、種類 (a)〜(c) は一次情報の URL を添える。**段階の列は `B`（マーカーの `tier=B` と同じ）のまま、B（事実）は「裏付け」の列の先頭に `B（事実）:` と書く**（例「B（事実）: ページ 463表示/28日。一次情報 <URL>（対象商品の一覧で猫砂を確認）」）。「トレンドで測った語」は、案1 なら `Yahoo推移: <語>（7日 N / 30日 M）`（Google トレンドでデータ不足だった語も並べる）、B（事実）なら `Yahoo推移: <語>（7日 N / 30日 M）・B（事実）` と書く。差し替えも削除もしなかった枠も、話題を確かめたら「最終確認日」を今日にする
3. §0 の 5 で集計したら、§1 の先頭に `T10集計` の行を足す（§0 の 5 の形）。§0 の 6 で B（事実）停止になったら同じく「B（事実）停止（確定 N・一般化/削除 M）」の行を足す
4. 試行中（第9版の実装後の最初の4回）は、ログ §5「T10 試行メモ（第9版）」に1行足す（実施ログではない。投稿の URL・本文・投稿者は書かない）
5. §4 の種は §3・§6 で回したものを追記し、確かめた種の欄を埋める

7. push とデプロイの完了後は `kura-content-improve` §6-3 と同じ:
   - **IndexNow を送る**（Bing 向け・AI が実行してよい）: `pnpm indexnow -- --url=https://www.kura-select.com/articles/<slug>/`。**`--url=` には必ず絶対 URL を渡す**（Git Bash では `/` 始まりの値がパスに変換されて壊れる。メモリ `feedback_gitbash_regex_file_filter`）。先に末尾に `--dry-run` を付けて送信先を確かめてもよい
   - **GSC の URL 検査で登録リクエスト**（ユーザー作業）をするよう伝える。済んだと言われたらログの「登録リクエスト」を日付に直す
