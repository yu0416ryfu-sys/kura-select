# KuraSelect 未登録記事の復帰

**目的は次の順に優先する。** ①Google に登録され、それが続くこと ②検索してきた読者が買う前の迷いを解消し、比較表から納得して選べること ③他の比較サイトや楽天の商品ページに無い情報があること。

当日に登録されても成功とは書かない。リクエスト直後の登録は続くとは限らず（hand-cream は一度消えた）、加筆とリクエストのどちらが効いたかも分けられない。

## 0. 入力と実行モード

- 入力は slug か URL を1つ。複数を渡されたら1本目だけ進め、残りは報告に書く
- **入力を `article.id` に直す。** `article.id` は `src/content/articles/` からの相対パスで `.md` を除いたもの（`insect-repellent-comparison`、`reviews/<名前>`）。入力どおりのファイルが無ければ `-comparison` を補って探し、それでも無ければ止まる（`-comparison` が付かない記事もあるので、補うのは見つからないときだけ）。URL は `https://www.kura-select.com/articles/<article.id>/`。ファイル・URL・台帳はこの形を使い、ログの slug 欄だけ `-comparison` を省く（既存のログに合わせる）。§8 の再確認でログの slug から URL に戻すときも同じ探し方をする
- 「未登録の再確認」と頼まれたら §8 の再確認だけを行う
- `docs/CONTENT_IMPROVEMENT_LOG.md`・`docs/CONTENT_IMPROVEMENT_CATALOG.md`・`docs/TODO.md` が無ければ止まる（`docs/` は gitignore 済みで、別 PC には無いことがある）

## 1. 今の状態を取る

ダッシュボードの値で判断しない（ファイル名の日付は GSC 確定日で、取得日ではない）。

1. `gsc_index_status` で `coverageState` と `lastCrawlTime` を取る
2. 確定日を `gsc_search_analytics`（`dimensions:["date"]`・直近10日）で実測し、直近28日の表示をページで絞って取る（終端は確定日）
3. Bing を `bing_page_stats` で取る。`startDate`＝確定日の27日前・`endDate`＝確定日・`rowLimit: 400`・`sortBy: "Impressions"` を指定し、対象 URL の週次の行を足す。**行が無いときは「未取得」と書き、0 と扱わない**
4. `src/content/articles/<article.id>.md` の frontmatter（`publishedAt`・`draft`・商品数）を読む

## 2. 判定する

上から順に見て、最初に当たったものに決める。

| 順 | 条件 | 動き |
|---|---|---|
| 1 | `coverageState` が `Submitted and indexed` | **止まる。** 登録済みと報告する。加筆の希望なら `kura-content-improve`、作り直しの希望なら同スキルの全面改稿モード（§9。集客の少ない記事に限る）を案内する |
| 2 | `coverageState` が noindex の除外（`Excluded by ‘noindex’ tag`）・`data/noindex-articles.json` に記載・`draft: true` | **止まる。** noindex のままでは登録リクエストが拒否される |
| 3 | 凍結中（`data/measurement-holds.json` の `releaseDate > 今日`。メモリ `project_measurement_holds` も見る）、`docs/TODO.md` §3 で日付つきで止められている、進行中の計画書の測定対象、公開14日以内 | **止まる。** 理由と解禁日を書く |
| 4 | ログ §6 に同じ記事の行がある | **止まる。** +28日 が空なら「再確認の日まで待つ」と書く。+28日 が埋まっていて未登録なら、統合・noindex・現状維持・再度の加筆のどれにするかを聞く |
| 5 | `Crawled - currently not indexed` / `Discovered - currently not indexed` 以外の状態 | **止まる。** 状態をそのまま報告する |
| 6 | `lastCrawlTime` が無い、または最後のクロールより後に本文が変わった（下の確かめ方） | **止まる。** 変更後のページを Google がまだ見ていない。加筆せず §7-7 の登録リクエストを案内する |
| 7 | 計画書5（`docs/IMPLEMENTATION_PLAN_INDEX_TRIAGE_LASTMOD_2026-10-11.md`）§4.1 の規則 1〜5 | 下の読み替えで判定する |

**順6の確かめ方。** 作者や件名では決めない（cron の商品更新も人のアカウントで記録されている）。`git log --since=<lastCrawlTime の1時間前> --format='%h %aI %s' -- <ファイル>` で候補を出し、各コミットの差分を見て、閉じる `---` より下の本文か `faqs` が変わったものだけを数える。1時間さかのぼるのは、デプロイに数分かかるため。

**順7の読み替え。** 規則1 と規則2 は**加筆**で §3 へ進む（Bing が未取得でも規則2 に当たれば進む）。規則3 は統合、規則4 は保留で**止まる**。規則5 に落ちたら、Bing が未取得なら判定保留、取得済みなら noindex 候補として**止まる**。規則の閾値はスクリプトにせず、計画書の表を読んで当てる（運用値で統計的な根拠は無いと報告に書く）。

止まったときは、判定の根拠の数字と次の選択肢を書いて、ユーザーの判断を待つ。

**ユーザーが「それでも加筆」と言えるのは順6 と順7 の止まりだけ。** そのときは §3 へ進み、ログに「規則〇だがユーザー判断で加筆」と残す。順1〜3 と順5 は上書きしない（順1 は `kura-content-improve`、順2 は noindex の解除の判断、順3 は CLAUDE.md §5.0.3 の手順へ回す）。順4 は聞いた結果に従う。

## 3. 原因の仮説を立てる

次の4つを調べ、根拠つきで書く。以後の加筆はこの結果に合わせる（全部を直す必要はない）。

| 観点 | 調べ方 |
|---|---|
| 同カテゴリとの重なり | 同カテゴリの記事の title を見る。上位の兄弟記事2〜3本を `filterPage` で1本ずつ取り（`dimensions:["query"]`）、対象記事の上位クエリと重なるかを見る。商品の重なりは計画書5の規則3の方法（`pc=` のデコード） |
| 内部リンク | `pnpm build` のあと `pnpm check-internal-links`。本文からの被リンク数と推奨リンク元を読む |
| 商品 | 商品数、用途の混入（説明の誤りは §5 で確かめ、見つかったら仮説に足す） |
| 本文 | 定型文の割合、検索された疑問に答えているか |

## 4. 疑問リストを作る

GSC を `dimensions:["query"]`・`filterPage`・`rowLimit: 5000` で**取れる全期間**（`startDate` は16か月前）取る。Bing は `bing_page_query_stats`（`page` に URL・`rowLimit: 400`）で取り、週×クエリの行をクエリごとに足す。読者の疑問に束ね、これを本文の設計図にする。表示の多い順に並べ、各項目に根拠（クエリと表示数）を付ける。

GSC にクエリが少ない記事は、購入者レビューとメーカーの Q&A から疑問を足してよい（根拠の欄にそう書く）。推測だけの疑問は入れない。

## 5. 調べる

サブエージェントに任せてよいのは収集だけ。判定・執筆・是正の判断は本体で行う（§9）。

- **商品**: `rakutenUrl` の `pc=` をデコードした `item.rakuten.co.jp` の URL をブラウザで開き、`document.body.innerText` から読む。**アフィリエイトリンクを踏まない**（自己クリックになる）。WebFetch は誤読するので使わない
- 確かめるのは、商品名・容量・区分・成分・使用方法・使えない条件・`features` / `pros` / `cons` / `recommendedFor` との一致。回数や日数を書くときは、商品名の「〇回分」ではなく使用方法の量で計算する
- **口コミ**: 商品ごとに楽天のレビューの星1〜3と星5を読み、テーマごとの傾向にまとめる
- **一次情報**: メーカー・業界団体・公的機関のページから、本文の断定に使う事実を集める
- 収集結果には URL と該当箇所の原文を必ず付け、スクラッチパッドにファイルで置く。本文に書くかどうかはこのファイルを根拠に決める

## 6. 書く

### 本文

- **H2 は疑問リストの項目に対応させる。** 対応しない H2 は足さない。文字数の目標は置かない
- 同カテゴリの記事と同じ説明を繰り返さず、§3 の結果に沿って、この記事だけの判断軸を書く
- 次のうち、そのジャンルで判断に効くものを入れる: 自作の計算表や換算／複数メーカーの表示を並べた比較／購入者レビューの傾向／原因の切り分け表や図
- 図解は判断が速くなるものだけ、最大3枚。書き方はカタログ T6
- 既存の本文は、誤りと重複に限って書き換えてよい（`kura-content-improve` より広い。理由はログに書く）
- `docs/CONTENT_IMPROVEMENT_CATALOG.md` の T1〜T9 の書き方・禁止を守る。不採用の型（「この記事が向いていない人」節・図解と重なる用途別の早見表）を書かない。T10 の枠（`trend-topic` マーカーの範囲）は触らない
- FAQ は frontmatter の `faqs[]` に書き、`pnpm inject-faqs` は使わない（本文に FAQ 見出しを書かない）。`faqs[].answer` の太字は `**`
- 価格・単価・レビュー件数・順位を本文と FAQ に書かない（CLAUDE.md §5.0.1）。効果効能を断定しない。「最安」「No.1」は根拠が無ければ書かない（§11）
- 本文の太字は、閉じる `**` の直前が約物なら `<strong>`（メモリ `feedback_markdown_bold_cjk`）

### 口コミの書き方

読んだ日と範囲を本文に書く。投稿文を引用せず、「〜という声がありました」の傾向にまとめる。評価点とレビュー件数の数値は書かない。効果の断定になる声は載せない。特定商品の欠点として断定しない。

### 商品（区分C）

- 全商品を §5 の結果と突き合わせ、`features` / `pros` / `cons` / `recommendedFor` の誤りを是正する。記事の `description` も事実の誤りだけ直す
- `name` は、実体と違うときだけ直す。`update-products` は `name` で商品を照合するので、次を守る。下の条件で変えられない商品の誤りは報告に書く
  - 実際の出品名にある固有の語と、容量の表記を残す（消すと更新のスキップや capacity の上書きが起きる）
  - 同じ記事の他の商品と同じ名前にしない
  - `grep -rlF "<現在の name>" reports/ai-capacity/processed reports/ai-capacity/pending reports/ai-matches/pending` に当たる商品は変えない（固定が名前の完全一致で外れる）。`reports/` が無くて grep がエラーになるときも変えない
  - `reviews/` の記事は dry-run の対象外なので、`name` を変えない
  - `reports/toAI/kura-product-match-ai/product-match-input-<今日>.jsonl` があれば `name` を変えない（dry-run が同じ日の入力ファイルを上書きするため）
  - 変えたら `pnpm update-products:dry -- --file=<ファイル名>.md` を実行する。「対象ファイル: 1件」を確かめる。`既存rakutenUrl` で始まる行か、1件以上の `capacity修正` が出たら、`name` を1件ずつ元に戻して再実行する。消えたらその `name` の変更が原因なので戻したままにする。戻しても消えなければ `name` の変更は残し、差分を報告に書く
- `price` / `capacity` / `pricePerUnit` / `rating` / `reviewCount` / `imageUrl` / `rank` は手で直さない。誤りは報告に書き、原因がスクリプトなら別作業にする
- 商品の追加・削除・差し替えはしない。必要なら報告だけする（区分D）

### 内部リンク

本文で文脈の通る箇所に、関連記事からこの記事へのリンクを1文で足す（1〜2本）。リンク元は `check-internal-links` の推奨から選び、推奨に無ければ同カテゴリの記事から選ぶ（推奨は本文被リンク0か孤立の記事にしか出ない）。登録済み（`gsc_index_status` で確かめる）・凍結中でない・noindex でない・`docs/TODO.md` で止められていない・進行中の計画書の測定対象でない記事に限る。リンク元が足せなければ、足さない理由を報告に書く。まとめ欄の羅列と `featuredArticles` の追加はしない。

## 7. 確認してデプロイする

1. **事実の照合**: 別のサブエージェントに、本文の断定を §5 のファイルと出典に照らして確かめさせる。商品に関する記述、数値、薬機法に触れる表現を優先する。指摘を直す
2. `data/content-dates.json` があれば `pnpm content:stamp` を実行する。`pnpm test` と `pnpm build` を通す。`pnpm preview` の localhost で、幅 375px の表示（図・表のあふれ）を確認する
3. `git status --short` と `git log origin/main..HEAD --oneline` を見る。**`git add` は対象ファイルを名指しする**（記事 MD・図・リンク元の記事・あれば `data/content-dates.json`）。ほかのセッションの作業を含めない
   - 件名は「<slug> に <何を> を加筆し、<是正内容> を是正」
4. push する。ただし次のときは push しない
   - `git log origin/main..HEAD --oneline` に自分のコミット以外がある
   - 今日が禁止日に当たる。`grep -n "禁止日" docs/TODO.md` で全件拾い、今日の日付と「〜デプロイ日」（日付未定のものはそのデプロイが今日予定か）を突き合わせる
   - 月曜の 12:00〜13:00 JST（cron の実行中）
   - 直前の `git pull --rebase` で競合が解消できない

   push しなかったら、理由を報告し、`docs/TODO.md` §3 に `待ち: <slug> の push（見直し MM-DD）` の日付で「push のあと `kura-index-recover` §7-5〜7 と §8-2〜4 を行う」の行を足す。ログの登録リクエストは「未」のままにする。見直し日は次に push できる日にする。再開するときも上の条件を確かめ直す。全部終えたら、この TODO の行をアーカイブへ移し、rebase でコミットのハッシュが変わっていればログを直す
5. デプロイの成功を `gh run list --workflow=deploy.yml --limit 3` で確かめ、本番は `curl` で確認する（足した見出しと図の URL）。**ブラウザで開かない**（GA4 に混入する）
6. `pnpm indexnow -- --url=https://www.kura-select.com/articles/<article.id>/` を送る（絶対 URL）
7. GSC の URL 検査で登録をリクエストする。Claude in Chrome で行い、できなければユーザーに依頼して報告に書く

## 8. 記録と再確認

実施した日に次を書く。**再確認の起点はデプロイ日にする。** push を保留した日は1だけ書き、2〜4 はデプロイの後に書く。

1. `docs/CONTENT_IMPROVEMENT_LOG.md` §1 の先頭に1行（型・足した節と根拠・是正内容・コミット・登録リクエスト）
2. 同じログの §6「未登録の復帰の経過」に1行（デプロイ日・slug・実施前の状態と最終クロール・判定・原因の仮説・+14日・+28日）
3. `docs/TODO.md` §3 に、デプロイ日+14日の `MM-DD` で「`kura-index-recover` の未登録の再確認」の行を日付順に足す。同じ日の行があれば足さない。翌年は `YYYY-MM-DD`
4. メモリ `project_measurement_holds` の「サイト横断の変更ログ」に1行注記する（加筆と区分C の同時実施。起点日・コミット・凍結は起こさないと書く）

凍結は起こさない。`data/measurement-holds.json` には書かない。

### 再確認（「未登録の再確認」で実行）

ログ §6 で +14日 / +28日 が空欄かつ期日が今日以前の行を全部、`gsc_index_status` で状態と最終クロールを取って書き込む。

- 処理した TODO の行は、`docs/TODO.md` の規則どおり `TODO_ARCHIVE_<年-月>.md` に移す
- +14日を書いた行があれば、その記事のデプロイ日+28日の `MM-DD` で TODO に行を足す。同じ日の行があれば足さない
- +28日で登録済みなら完了
- **+28日で未登録なら、自動で加筆しない。** §1 の数字を取り直し、統合・noindex・現状維持・再度の加筆のどれにするかをユーザーに聞く
- 結果を仮説と並べて報告する。ただし因果は判定しない

## 9. 作業の分担

ユーザーの指示により、質を落とさない範囲で軽いモデルのサブエージェントを使う。**どの担当にも次を指示する: 本番のページを開かない／アフィリエイトリンクを踏まない／楽天を WebFetch で読まない。**

| 作業 | 担当 |
|---|---|
| 楽天の商品ページとレビューの収集、メーカー資料の抜き出し | sonnet。URL と原文の添付を必須にする |
| `pnpm test` / `pnpm build` / デプロイの確認 | haiku か sonnet。要点だけ報告させる |
| 事実の照合 | 本文を書いていない別のサブエージェント（sonnet 以上） |
| 判定、仮説、本文、図解、是正の判断 | 本体 |

## 10. 報告

次の順で短く書く: 判定／原因の仮説／足した節と根拠／是正した誤り／デプロイと登録リクエストの状態／次の確認日／未完了の作業。当日の登録結果は「成功」と書かず、再確認の日付を添える。

## 11. やらないこと

- 登録状態を確かめずに加筆する
- title / description の改稿（事実の誤りの是正を除く）、商品構成の変更、テンプレ・構造化データの変更
- 凍結を起こす、効果を判定する
- +28日の確認とユーザーの判断を経ずに、同じ記事へもう一度全面加筆する
