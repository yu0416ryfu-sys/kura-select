# 計画書レビューの観点表（第2巡で読む）

第1巡（自由レビュー）の指摘を書き出してから読む。第1巡の前に読まない。指摘の「観点」欄には、この表の節番号に `L` を付けて書く（`L8.1` など）。

## 1. 種類の判定

当てはまるものをすべて選ぶ。

| 記号 | 種類 | 目安 |
|---|---|---|
| S | スクリプト | `scripts/`・`scripts/lib/`・`tests/` を変える |
| T | テンプレ・CSS・構造化データ・サイト設定 | `src/layouts/`・`src/components/`・`src/pages/`・`src/styles/`・`src/lib/`（`site.ts`・`capacity.ts`・`structured-data.ts` など）・`src/content.config.ts`・`astro.config.mjs`・`public/`・`package.json` と lockfile の依存更新など、複数ページに効く |
| K | スキル・自動化 | `.claude/skills/`・`.agents/skills/`・`CLAUDE.md`・`AGENTS.md`・`scripts/hooks/`・mod・`.claude/settings*.json`・`.github/workflows/` を変える |
| C | 記事・コンテンツ | `src/content/` の記事・カテゴリを変える |
| D | デプロイ日 | 本番に出る変更すべて（T・C、および画面や出力に効く S・K） |
| E | 測定 | 効果を測る、凍結を起こす・解く、凍結中の記事に触れる |

- どれにも当たらないときは T とみなす
- `data/` の台帳（`ad-placements.json`・`content-dates.json`・`price-report/`・`measurement-holds.json` など）を変える計画は、その台帳を読むスクリプト・テンプレの種類（S・T）に入れる。本番の出力に効けば D、凍結の判定に効けば E も当てはめる
- E は、本番に出るなら D と一緒に当てる。本番に出ない E（凍結台帳だけを変える計画など。`measurement-holds.json` を読むのは `scripts/` と hook だけ）は D を外す

## 2. 種類別に読むもの

- S: 変更するロジックを直接テストしているテスト（他は名前の確認だけ）
- K: 対象スキルの `.claude/skills/` と `.agents/skills/` の両方。役割が隣り合うスキルの description。`.github/workflows/` を変えるなら対象の workflow
- C: `data/measurement-holds.json` の最上位 `prohibitions[]`（`slugs`・`scope`。商品追加の禁止で期限なし）
- D: `data/measurement-holds.json` の `holds[]`（`slug` / `slugs`・`releaseDate`・`arm`・`measures`）、`docs/TODO.md` の禁止日（`grep -n "禁止日" docs/TODO.md` で全件。日付が決まっていない禁止日も拾う）。凍結が何を測っているかの正はメモリ `project_measurement_holds`（読めない環境では JSON の `measures` で代え、「メモリ未確認」と書く）
- E: D に加えて、今動いている測定窓。`holds[]` の有効な行（`releaseDate` > 今日）と `docs/TODO.md` から引き、その施策の計画書の測定窓の節を読む（計画書が名前を挙げた計画書に限らない）。`pnpm search-status -- --offline --window=予定日:予定日`（予定日が影響期間に入るかが出る。保存分の取得日は `data/google-search-status.json` の `updatedAt` で、それも書く）

## 3. 共通（全種類）

- 目的・変更範囲・手順が現行コードと一致しているか。計画書が書いている件数・実測値を1つ以上測り直して合っているか
- 計画が言及していない副作用は無いか（第1巡の grep の結果で判断する）
- やりすぎていないか。もっと簡単な代わりの案は無いか
- 受入確認が実在するコマンド・確認方法で書かれているか。計画の他の節と食い違って**必ず落ちる／必ず通る**確認になっていないか。コマンドが Windows で動くか（Git Bash で `--file=/正規表現/` や `--url=/パス/` が壊れる・PowerShell 5.1 で日本語の集計が化ける）
- ロールバックの手順があるか。途中で失敗したときに半端な状態が残らないか
- 1計画1デプロイになっているか。他の変更とコミット・push を分ける手順があるか
- 成果物を gitignore された場所（`docs/`・`reports/`）にだけ置き、コミットされないままになっていないか
- データ源（GSC・GA4・Bing・楽天 API・`reports/`）が欠けている・取れない・遅れているときに、止まる・誤判定する・黙って0として扱う、が起きないか
- 確認の手順で本番に大量アクセスしないか（GA4 に混入する）。複数ページの確認は `dist/` か localhost で行い、本番で開くのは数ページに限っているか
- 過去に没・見送りにした案をもう一度出していないか（メモリの `project_*_rejected`・`project_seo_lessons`。読めない環境では「メモリ未確認」と書く）。計画全体の価値は第0巡で判定済みなので、ここでは計画の一部の手順や節が没案と重なるかだけを見る

## 4. S スクリプト

- import/export の過不足、ループ内変数のスコープ、型と実データ（空文字と null など）、ファイル拡張子
- 比較の両辺が同じ正規化を通っているか
- 既存のガード（早期 return・条件分岐）や `review` / `rejected` / `matched` などの状態遷移を、計画の手順がすり抜けたり壊したりしないか
- dry-run と write の違い。**dry-run で確かめられることを write でしか確かめない計画になっていないか**。`.bak` の生成と途中失敗時の挙動
- 記事 frontmatter・Zod スキーマ（`src/content.config.ts`）への影響。スキーマを変えるなら、全記事に効く影響範囲を示してユーザーに確かめる手順があるか
- テスト不足: 変更したロジックにテストを足す手順があるか（既存のテストが通るだけで済ませていないか）
- テストの直接性: テストが実装の関数を import しているか。テスト側にロジックの複製が無いか。helper を切り出してテストしていても、呼び出し元がその helper を使っていない、ということが無いか
- 外部 API の負荷（楽天の 429・`--concurrency`・`--api-interval`）。秘密情報（`.env`・アプリ ID・キー）をコード・ログ・レポートに書かないか

## 5. T テンプレ・CSS・構造化データ・サイト設定

- 影響範囲の grep に漏れが無いか（`reviews/` 配下の記事が同じレイアウトを通るか、など）
- 内部リンクが `url()` 経由か。生成 URL・JSON-LD・CSS の受入が `dist/` の実出力（本番 HTML なら数ページ）で書かれているか（ソースの grep だけで済ませていないか）
- `client:load` を使っていないか。新しい island を作るなら理由が書かれているか
- 色・フォントが semantic token か（`#xxx` や `text-blue-500` の直書きが無いか）
- Lighthouse 95+ の目標を崩さないか。広告の載る記事では CLS・TBT の停止条件と干渉しないか
- アフィリエイト表記・`rel` の中央管理を壊さないか
- 全記事で読者に見える内容が変わるなら `pnpm content:stamp`、見える内容が変わらない一括処理なら `-- --keep-dates` の要否が書かれているか

## 6. K スキル・自動化

- `.claude/skills/` と `.agents/skills/` の両方を同じ内容に直す手順があるか（スキルのディレクトリ内の全ファイル）
- 行番号・節番号・旧い語で指した箇所の**書き残し**を見つける確認（grep の式）が受入にあるか
- 他のスキル・`CLAUDE.md`・`AGENTS.md` と役割が重ならないか、ルールと矛盾しないか
- `CLAUDE.md` を変えるなら、Codex 用の `AGENTS.md` にも反映する（または反映しない理由を書く）手順があるか
- description を変えるとき、呼び出されるべき依頼で呼ばれ、隣のスキルの依頼で呼ばれない書き方か
- workflow を変えるとき、無効化中の楽天同期 cron（`update-products.yml`）を有効に戻していないか

## 7. C 記事・コンテンツ

- 本文・title（件数以外）・description・faqs を変えるなら `pnpm content:stamp` を同じコミットに入れる手順があるか
- 本文や `faqs[].answer` に価格・単価・レビュー件数などの数値を書かせていないか（数値の正は frontmatter `products[]`）。FAQ は frontmatter に書くか
- 変更が区分 A〜D のどれかが書かれているか。D（商品構成の意図的変更）を凍結中の記事に入れていないか。`prohibitions` に載った記事に商品を足していないか
- 凍結中の記事を Bash / PowerShell で書き換える手順が無いか（凍結ガードの hook をすり抜ける）
- 「最安」「No.1」の根拠、薬機法の断定

## 8. D デプロイ日・E 測定

### 8.1 D（本番に出る変更）

- デプロイ予定日が書かれているか。無ければ major とし、以降の項目は今日の日付で仮に判定して「仮」と書く
- `data/measurement-holds.json` で `releaseDate > デプロイ予定日` の行と対象が重ならないか。重なるなら、その凍結が測る指標に作用するかが書かれ、作用するならユーザーに可否を聞く手順があるか
- 対照群（`arm: "control"`）の記事に触れていないか
- `docs/TODO.md` の禁止日（日付未定のものを含む）と重ならないか。月曜（楽天同期）を避けているか
- 測らないなら: 週次分析でデプロイ日を区切りとして併記するだけになっているか

### 8.2 E（測る・凍結を起こす/解く・凍結中の記事に触れる）

- 今動いている他の施策の後窓（「サイト全体の変更を入れない」などの指定）と重ならないか。重なる施策の計画書の側にも1行書く手順があるか
- Google 検索のコアアップデート: デプロイ予定日が影響期間（完了後14日を含む）に入るなら major（変動期は新しい施策を打たない）。窓が後で重なったときの扱い（判定は暫定）が書かれているか
- **新しい凍結を起こしていないか。** 凍結・判定を続けてよいのは「新規記事の公開2週判定」と「主指標と成否基準を事前に決めた単独施策」だけ。記録だけの凍結を起こしていないか。コホートを組んでいないか
- 測るなら:
  - 主指標・成否基準・窓が事前に書かれているか。**主指標が既存の CLI・スナップショットで後窓に実際に計算できるか**。GSC の確定日の実測、GA4 の T-1 の扱い、サイト全体での正規化が書かれているか
  - 記帳: 両方の台帳（JSON とメモリ）に書く手順があるか。`releaseDate` を解除日の翌日にしているか。`searchNeed` を施策の前に書くか。`tests/measurement-holds.test.ts` が通るか

## 9. blocking の例

- 参照している関数・型・script・ファイルが存在しない、または名前が違う。節番号・行番号は、実装がその番号を頼りにしているときだけ（ただの書き間違いは minor）
- 計画どおりに書くと既存のテストが落ちる。確認に使う pnpm の script 名が `package.json` に無い
- 状態遷移や dry-run / write の分岐を壊す
- 受入確認が計画の他の節と食い違い、必ず落ちる
- 測る施策なのに、主指標が既存の CLI で後窓に計算できない
- 凍結中の記事・対照群・禁止日・他の計画の後窓と重なり、凍結が測る指標に作用しうるのに扱いが書かれていない（作用しないことが明らかなら major）
- 記録だけの凍結・コホートを起こす
- スキルの片方のディレクトリしか直さない。行番号で指した旧い記述が残るのに、それを見つける確認が無い
- 手順が push に別の変更を巻き込む（分ける手順が書かれていないだけなら major）
