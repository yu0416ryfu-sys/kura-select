# KuraSelect 週次アクセス分析スキル

**このスキルの目的は「毎週同じ品質のレポートを出すこと」。** 分析の切り口を毎回変えないこと自体が成果物の価値である。気の利いた新しい見方を思いついても、テンプレの枠内に収める。

## 0. 前提の確認（ここを飛ばさない）

1. `reports/weekly/` に**当日または直近の** `snapshot-<確定日>.md` があるか確認する
2. 無い、または確定日が7日以上前なら、**先にユーザーへ実行を促して止まる**

```bash
pnpm weekly:snapshot
```

3. スナップショットは `.md`（ダイジェスト）を主に読む。ページ別・クエリ別の全行が要るときだけ同名の `.json` を読む
4. **定点観測（§3 サイト全体・§4 記事別）では GSC / GA4 / Bing の MCP を自分で叩き直さない。** 確定日・窓・正規化子はスナップショットが唯一の正
5. **例外は §2 の施策判定だけ。** 施策判定は §2 のルールどおり**起点日で窓を切る**のが優先で、スナップショットの今週/前週は起点日と一致しないことが多い。この場合に限り MCP で窓を取り直してよい（2026-08-24 に方針確定）。ただし次を守る:
   - **確定日はスナップショットの値を使う**（`gsc_search_analytics` を `dimensions:["date"]` で叩き直さない）。窓の終端は確定日を超えない
   - サイト全体（正規化子）は必ず `dimensions: []` で取る。ページ別は `filterPage` を使う（次元の行を足し上げない）
   - **レポートの冒頭に「§2 の判定のみ起点日で窓を切り直し、MCP で個別取得した」と明記する**

## 1. 参照順（この順序を崩さない）

| # | 参照先 | 何を取るか |
|---|---|---|
| 1 | `reports/weekly/snapshot-<確定日>.md` | 確定日・窓・サイト全体・ページ別・クエリ・GA4・Bing |
| 2 | メモリ `project_measurement_holds` | 凍結中の記事と解除日。**触れてよい記事の判断はここが正** |
| 3 | `docs/TODO.md` §2 凍結表 / §3 カレンダー | 今週が判定期限の施策 |
| 4 | 前回の `docs/ACCESS_ANALYSIS_*.md`（最新1本） | 前回の宿題と継続観測点 |
| 5 | `reports/gsc-harvest/baseline-*.json` | 施策判定の比較元（起点日より前の baseline を使う） |
| 6 | `reports/affiliate-performance-log.md` | 送客の実績（GA4 クリックと管理画面の乖離） |

4 と 5 は、判定期限が来ている施策がある週だけ読む。無い週は飛ばしてよい。

## 2. 判定ルール（例外なし）

- **窓は施策日で切る。** スナップショットの今週/前週はあくまで定点観測。個別施策の判定は起点日で窓を分け、`baseline-*.json` と比べる
- **正規化する。** ページ別の `正規化クリック` / `正規化表示` 列を見る。素の増減で語らない
- **`判定可` が `×(実数一桁)` の行は判定に使わない。** 「増えた/減った」と書かず「母数不足で判定不能」と書く
- **ベースラインが無い期間は「判定不能」と正直に書く。** GSC の期間比較UIや体感で補わない
- **凍結中の記事に施策を提案しない。** 解除日を書いて次週以降に送る。ただし `CLAUDE.md` §5.0.3 の区分B（リンク切れ）・区分C（誤表示）は例外
- **提案は上位3件まで。** 4件目以降は「今週は出さない」と書く

## 3. 出力

- 出力先: `docs/ACCESS_ANALYSIS_<実行日>.md`（例 `ACCESS_ANALYSIS_2026-08-24.md`）
- 構成は `templates/report-template.md` の見出しを**そのまま**使う。見出しを足さない・減らさない・並べ替えない
- 該当が無いセクションは削除せず「なし」と書く
- 数値は必ず出典（スナップショットのどの表か）が辿れる形にする

## 4. 提出前のセルフチェック（全項目を満たすまで出さない）

- [ ] 冒頭に「GSC の最新確定日は YYYY-MM-DD」を書いたか
- [ ] 測定窓（開始日・終了日・日数）を明記したか
- [ ] サイト全体の数字を `dimensions: []` 由来（スナップショット §1、または §2 判定で取り直した窓）から取ったか。ページ別やクエリ別の合計で代用していないか
- [ ] §2 の判定で窓を取り直した場合、冒頭にその旨と取得方法を書いたか
- [ ] ページ別の増減を**正規化後**の値で述べたか
- [ ] クリック実数が一桁の比較を判定に使っていないか
- [ ] 凍結中の記事に施策を提案していないか（`project_measurement_holds` と突き合わせたか）
- [ ] 判定期限が来ている施策を全部拾ったか（`docs/TODO.md` §3）
- [ ] 提案は3件以内か
- [ ] 「〜な気がする」「おそらく改善」のような数値の裏付けが無い表現を消したか
- [ ] 施策を打つ提案をした場合、`project_measurement_holds` への追記（起点日・解除日・指標）を宿題として明記したか

## 5. やらないこと

- スナップショットを作り直す（データ取得はスクリプトの仕事。分析はスキルの仕事）。§0-5 の例外は「判定用に窓を取り直す」ことであって、スナップショットの再生成ではない
- 記事ファイルの編集（このスキルは読むだけ。編集は判定が済んでから別作業で行う）
- 新しい指標や切り口の追加（提案として書くのはよいが、今週のレポート構成は変えない）
