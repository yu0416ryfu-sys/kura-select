# KuraSelect 話題の追従（T10）

**このスキルの目的は、SNS・世間で話題になっている事柄を、投稿を貼らずに「読者の疑問への答え」として記事に反映し、世間の動向に合った情報を出すこと。** 古くなった話題を残さないことを、新しい話題を入れることより優先する。

流れは **期限切れの処理 → 話題を集める → ふるい分け（§4）→ GSC で裏付け（§3）→ 提案して止まる → 承認分だけ実施 → 記録**。提案のあと、ユーザーの判断を待たずに記事を編集しない。

計画書: `docs/IMPLEMENTATION_PLAN_TREND_TOPICS_2026-10-25.md`。型の定義（書き方・禁止）は `docs/CONTENT_IMPROVEMENT_CATALOG.md` の T10。

## 運用の決まり（2026-10-25 ユーザー決定）

- 話題には**日付を書く**。**3か月で期限切れ**にし、時期を問わない書き方に直すか削除する
- **1記事1枠**。新しい話題は古い枠と**差し替え**る（積み上げない）
- **週1回**、人間が実行する（`docs/TODO.md` §8 継続ルーチン: 毎週月曜・週次分析の後）
- **数値を書かない**（価格・単価・割合・順位・件数。CLAUDE.md §5.0.1）
- ログは `docs/CONTENT_IMPROVEMENT_LOG.md` に**一本化**する（§1 実施ログ・§3 有効中の話題枠・§4 新規記事の種）
- 採用する話題は **GSC の検索クエリの裏付けで3段階に分ける**（下の「採用の段階」）。0表示の話題は段階C の条件をすべて満たすときだけ
- 一次情報リンクを単独の施策として足すことはしない。T10 の中で根拠が要るときだけ公式の出典を1つ添える
- X は**ユーザーがログイン済みの Chrome を Claude in Chrome で読むだけ**（1回5検索まで・投稿/いいね/リポスト/フォロー/DM/設定変更をしない）。Yahoo!リアルタイム検索・Google トレンドは補助。本数を増やしても X の検索回数は据え置き、足りない分は Yahoo!リアルタイム検索で補う

### 上限（1回の実行あたり）

- **新規・差し替えは合計5本まで**。そのうち段階B は2本まで、段階C は1本まで
- **期限切れ（§1 の 1〜5）と見直し期限（§1 の 6）の処理は上限の外**（後始末で新しい枠を減らさない）。上限の外になるのは「一般化・削除・A への昇格・見直し期限の延長」まで。**同じ記事に新しい話題を入れるなら、それは通常の新規として上限と段階の条件に数える**（その記事の14日ルールだけは、直前の後始末を実施に数えない）
- 上限の外の処理も**1回あたり5本まで**。期限・見直し期限の古い順に処理し、残りは次回に回す（実行が止まった週のたまり分を一度に出さない）
- **条件を通った話題が上限に満たなければ、そこで止める。** 本数を埋めるために条件を緩めない

### 採用の段階

GSC は §3 の取り方。表示は話題の言葉を含むクエリの、対象記事のページでの直近28日の合計。

| 段階 | 採用の条件 | 枠の扱い |
|---|---|---|
| **A（確度高）** | **3表示以上** | 期限は入れた日＋3か月 |
| **B（先回り）** | **1〜2表示**、かつ X で話題になっており、かつ Google トレンドで**伸び** | 期限3か月に加え、**見直し期限＝入れた日＋4週** |
| **C（読者が困る事実）** | **0表示**でも、次の3つを**すべて**満たす: ① 読者が買う前・使うときに困る事実（仕様変更・販売終了・品薄・リコール・成分や規格の変更など。雑談的な流行は対象外）② X で話題になっており、かつ Google トレンドで伸び ③ メーカー・公的機関の一次情報で事実を確かめられる | B と同じ（見直し期限＝入れた日＋4週） |

- 「X で話題」は、Claude in Chrome で X を見たときに加え、**Yahoo!リアルタイム検索に出た X の投稿でも満たす**（どちらも投稿が複数あり、ここ1〜2週に集中していること）
- 「Google トレンドで伸び」は、日本・過去90日で直近の値が期間の前半より高いこと。**トレンドが「データ不足」なら伸びではない**（B・C は採用しない）
- 段階A・B の候補が出た記事に C の枠があれば、A・B を優先して差し替える（14日ルールは通常どおり）

### 見直し期限の判定（B・C 共通）

**スナップショットの確定日が見直し期限以降**になってから行う（窓は確定日までの28日なので、枠を入れる前の日が混ざらない）。上から順に当てはめて、最初に当たったものに決める:

1. 28日で **3表示以上** → **A に上げる**（`review=`・`extended=` を消し `tier=A`。期限は入れた日＋3か月のまま）
2. **1〜2表示** で、まだ延長していない → **B にして見直し期限を4週延ばす**（`tier=B`・`extended=1`。元から B でも C から来たものでも1回だけ。**延長後の見直し期限＝旧見直し期限＋28日**。判定が遅れても判定日から数えない）
3. それ以外（0表示、または延長済みで2表示以下）→ **削除する**

削除した記事に別の話題を入れたいときは、§3 の採用条件を通った候補として、その回の新規の上限に数える。通った候補が無ければ削除だけで終わる。

## 0. 前提の確認（ここを飛ばさない）

1. `docs/CONTENT_IMPROVEMENT_CATALOG.md` と `docs/CONTENT_IMPROVEMENT_LOG.md` があるか確認する。無ければ止まってユーザーに伝える（docs/ は gitignore 済みで、別 PC には無いことがある）。ログに §3「有効中の話題枠」・§4「新規記事の種」が無ければ、それも伝えて止まる
2. `reports/weekly/` の最新の `snapshot-<確定日>.md` の確定日を見る。**確定日が7日より前なら `pnpm weekly:snapshot` の実行を促す**（実行するかはユーザーに聞く。古いまま進めるなら提案の冒頭にその旨を書く）。この確定日を、§1 の見直し期限の判定と §3 の GSC の窓の終端に使う
3. 今日がデプロイ禁止日かを確かめる。禁止日は一覧が無く TODO §3 の備考欄に散らばっているので、`grep -n "禁止日" docs/TODO.md` で全件拾い、今日の日付と「〜デプロイ日」（日付未定のものはそのデプロイが今日予定か）を突き合わせる。禁止日でも提案と実施（コミットまで）はしてよいが、**push は禁止日を避ける**と提案に書く
4. 今日が月曜なら、cron（`update-products.yml`・03:00 UTC＝12:00 JST）が bot コミットを積む。**push は 12:00〜13:00 JST を避け、push の直前に `git pull --rebase` で bot コミットを取り込む**と提案に書く

## 1. 期限切れ・見直し期限の処理（毎回最初）

1. ログ §3 から `期限 <= 今日` の行を拾う
2. 念のため次のコマンドで、ログに無い枠・ログと `tier` / `added` / `review` / `extended` / `expires` が違う枠が無いか突き合わせる。**`.md.bak` を拾わないよう `--include` を必ず付ける**。ずれていたら提案の冒頭に書く
   ```bash
   grep -rn --include="*.md" "trend-topic:start" src/content/articles/
   ```
3. 期限切れの枠ごとに「一般化して残す（時期を問わない書き方に直し、マーカーと見出しの日付を外す）」か「削除する」かを提案に含める。一般化した内容はもう T10 ではないので、§3 の行を消し §1 に「T10 期限切れ→一般化」と記録する
4. **期限切れの処理は §4 の「14日以内に実施した記事」の除外にかからない**（古い日付を残さないことを優先する）
5. 期限切れの枠がある記事が凍結中なら、編集しない。その凍結が何を測っているかを先に確かめ（`data/measurement-holds.json` とメモリ `project_measurement_holds`）、区分C（事実として誤った表示の修正）に当たるかどうかも含めてユーザーに聞く（CLAUDE.md §5.0.3。古くなっただけでは誤りとは限らない）。対照群なら触らず、解除日まで提案に「期限切れ・凍結のため保留」と書き続ける
6. **見直し期限の処理**: ログ §3 から `見直し期限 <= スナップショットの確定日` の行を拾い（確定日が見直し期限に届いていない行は次回に回す）、§3 の取り方で GSC を取り直して「見直し期限の判定」（A に上げる・延長（B・C 共通・1回）・削除）を提案に含める。期限切れと同じく**上限の外・14日ルールの対象外**で、凍結中なら 5 と同じ扱いにする

1〜6 の処理は合わせて**1回5本まで**。期限・見直し期限の古い順に取り、残りは次回に回す。

## 2. 話題を集める

| 順 | 情報源 | ブラウザ | 上限・ルール |
|---|---|---|---|
| 1 | X の検索（話題の言葉 ＋ ジャンル語。「最新」タブ） | **Claude in Chrome**（ユーザーのログイン済み Chrome） | 1回の実行で**検索5回まで**。スクロールは各検索で数画面まで。読むだけ（投稿・いいね・リポスト・フォロー・DM・設定変更・通知の操作をしない）。ログインが切れていたら X を飛ばす（ログインし直さない） |
| 2 | Yahoo!リアルタイム検索 | 内蔵ブラウザ | 補助。ログイン不要。X の検索回数を超える分はここで補う |
| 3 | Google トレンド（日本・過去90日） | 内蔵ブラウザ | 需要の向き（伸び・横ばい・下降）を見る。CAPTCHA やボット判定が出たらその情報源を飛ばす（突破しない） |

- 検索語は、ログ §3 にある既存の枠の話題と、凍結・noindex でない記事のジャンル語から作る（最大5語）
- 集めた話題はチャットにメモするだけで、投稿の URL・本文・投稿者をファイルに保存しない
- 「X で話題」「Google トレンドで伸び」の判定は「採用の段階」の定義に従う

## 3. GSC で裏付ける

- **§4 のふるい分けを先に行い**、条件に当たらなかった候補の記事（**最大8本**＋見直し期限の記事。段階は GSC の後に決まるので、上限の5本より多めに取る）ごとに、`gsc_search_analytics`（MCP `mcp__gsc__gsc_search_analytics`）を次の条件で取り、話題の言葉を含むクエリを探す（`kura-content-improve` §3-2 の T1 と同じ取り方）
  - `dimensions:["query"]`
  - `filterPage: https://www.kura-select.com/articles/<slug>/`
  - 直近28日（**終端はスナップショットの確定日**。確定日を叩き直さない）
  - `rowLimit: 5000`
- サイト全体を `["query","page"]` で1回取る方法は使わない（5000 行で打ち切られ、少ない表示の行から落ちるため）
- 返ってきた行が 5000 ちょうどなら打ち切りの可能性があると提案に書き、閾値近くの話題は採用しない
- 採用の条件: 話題の言葉を含むクエリの、対象記事のページでの28日の表示（**表記ゆれは候補ごとに列挙して合算**）で段階を決める。3表示以上＝A、1〜2表示＝B の候補、0表示＝C の候補。B・C はさらに「採用の段階」の条件をすべて確かめる
- 段階のどれにも当たらない話題は T10 に使わない。既存記事に受け皿が無いジャンルの話題は §6 の種に回す

## 4. ふるい分け（候補から外す記事）

`kura-content-improve` §2 と同じ条件で外す。外した理由はまとめて1行で書けばよい。

- 凍結中（対照群を含む）。`data/measurement-holds.json` の `releaseDate > 今日` の行の slug と、メモリ `project_measurement_holds` の**両方**を見る
- noindex 中（`data/noindex-articles.json`）
- `docs/TODO.md` §3 で日付つきで止められている（その日付を書いて次回以降に送る）
- `docs/TODO.md` §3 で進行中の計画書の測定対象（前窓・後窓）に入っている記事。後窓の終わりが未確定なら「後窓未確定」と書いて外す
- **14日以内に実施した記事**（ログ §1。T10 を含むすべての型。ただし直前の T10 の後始末（一般化・削除・昇格・延長）だけの行は数えない。`kura-content-improve` 側は数える）
- 実施ログ §2 で見送られ、理由がまだ解消していない記事×型
- `draft: true` の記事

加えて、次の話題は使わない:

- 炎上・事故・リコールの話題で一次情報が見つからないもの
- 効能の主張が中心の話題（例:「〇〇で肌荒れが治った」）
- 記事のテーマ（title が答えている問い）から外れる話題

## 5. 提案して止まる

チャットに次の形で出す。ファイルは作らない。

```
## 今週の話題の提案（YYYY-MM-DD）

前提: スナップショット確定日 YYYY-MM-DD ／ 今日の push: 可・不可（理由）／ X: 検索 N 回（ログイン切れなら「飛ばした」）
マーカーとログ §3 の突き合わせ: ずれなし（あれば内容）

### 新規・差し替え（最大5件・B は2件・C は1件まで）

| # | 記事 | 話題 | 段階（A/B/C） | 裏付けクエリ（表示/28日）または一次情報（C） | X/トレンドで見たこと（要約） | 新規 or 差し替え | 書く内容（見出し案） | 注意 |
|---|---|---|---|---|---|---|---|---|
| 1 | ... | ... | A | 「〇〇 △△」4表示・「〇〇△△」1表示 | X で ここ1週に複数・トレンド伸び | 新規 | ## 〇〇が話題ですが、△△は気にした方がいい？（2026年10月時点） | 数値は比較表へ誘導 |

### 期限切れ・見直しの処理（件数に数えない・最大5件）

| # | 記事 | 話題 | 期限切れ処理 or 見直し | 判定（一般化・削除・A へ昇格・延長） | 根拠（表示/28日など） |
|---|---|---|---|---|---|

候補から外した記事: 凍結中 N本、14日以内に実施 N本、TODO で停止中 N本、テーマ外の話題 N件
新規記事の種（§6）: 追記 N件・判断を埋めた種 N件
```

- **新規・差し替えは5件まで（B は2件・C は1件まで）。** 期限切れ・見直しの処理は件数に数えず、別の表にまとめる
- 割合・件数・価格などの数値が見出し案・本文案に入っていないかを提案の時点で確かめる（本文 lint は円表記しか止めない）
- 点数はカタログの値（6.5）を使う。記事ごとに点数を作り直さない
- 出したら止まり、ユーザーの判断（どれをやるか・見送るか）を待つ

## 6. 新規記事の種（③）

- 既存記事に受け皿が無いジャンルの話題は、ログ §4 に「確認待ち」で記録する（初めて見た日・話題（ジャンル語）・情報源）
- 「既存記事に受け皿が無い」は page 単位ではなく、**サイト全体の query 次元**（`kura-article-recommend` の採択基準と同じ測り方）で判断する
- **初めて見た日から14日以上**たった種について、実行のたびに次の3点を確かめて「2週後の確認日」「需要の向き」「楽天で同用途5件以上」「判断」を埋める:
  1. Google トレンドで需要が**伸び・横ばい**（下降なら見送り）
  2. ジャンル語が**一般名詞**（固有の商品名・流行語は見送り）
  3. 楽天で**同じ用途・同じ年齢層**の商品が5件以上（メモリ `feedback_no_mixed_use_rankings`）
- 3点を満たした種は「kura-article-recommend へ回す」、満たさなければ「見送り（理由）」とする
- 回した種も、recommend の基準（サイト全体の query 次元で、テーマ語＋選択系語のクエリが28日で表示30以上）を通らなければ見送りになる。**受け皿の無い話題は表示が立たず、見送りになるのが普通。** 種は「需要が育ったジャンルを見逃さないための記録」であって、候補を増やす仕組みではない

## 7. 承認された分だけ実施する

`kura-content-improve` §5 の 1〜6 に従う:

1. **1記事1コミット。** 編集の前に記事を Read する（CLAUDE.md §13）
2. カタログ T10 の「書き方」「禁止」に従う（下にも要点を書く）。既存の本文・見出しは書き換えない（差し替え・期限切れの処理で触るのは `trend-topic` マーカーの範囲だけ）
3. 凍結中の記事を Edit しようとして hook（`freeze-guard`）が止めたら、作業を止めてユーザーに伝える（ふるい分けの漏れ）
4. `pnpm test` と `pnpm build` を通す（本文 lint・Zod・OGP）。出力が長いのでサブエージェントに任せてよい（メモリ `feedback_token_saving_subagents`）。計画書5 Part A（`data/content-dates.json`）が main に入っていて `pnpm test` が落ちたら `pnpm content:stamp` を実行し、更新された台帳を同じコミットに入れる
5. コミットメッセージは日本語で、「<slug> に <話題> の H2 を加筆」「<slug> の話題枠を <新しい話題> に差し替え」の形にする（期限切れ・見直しは「<slug> の話題枠を一般化」「<slug> の話題枠を削除」など）
6. push はユーザーの指示があってから。禁止日は避ける

### 書き方の要点（カタログ T10）

- 位置は、見出しが**ちょうど `## まとめ`**（`^## まとめ$` の完全一致。「## まとめ買いの〜」は当たらない）の H2 の直前。完全一致の見出しが無い記事（2026-10-25 時点で rakuten-marathon-guide・water-server-comparison・water-server-delivery-comparison・reviews/shampoo-pantene-damage-care-review の4本）は、本文の最後の H2 の節の後。確かめるコマンド:
  ```bash
  grep -n -E "^## まとめ$" src/content/articles/<slug>.md
  ```
- 見出しは `## <話題の言葉を含む疑問>（YYYY年M月時点）`。見出しの直後の1〜2文で答えを先に書く
- 枠の前後をマーカーで囲む:
  ```markdown
  <!-- trend-topic:start tier=B added=2026-10-25 review=2026-11-22 expires=2027-01-25 -->
  ## 〇〇が話題ですが、△△は気にした方がいい？（2026年10月時点）

  答えを先に1〜2文。……
  ```

- `tier` は A / B / C。`review` は B・C のときだけ書く（初回は入れた日＋28日）。延長したら `extended=1` を足し `review` を旧見直し期限＋28日にする。A に上げたら `review=` と `extended=` を消し `tier=A` に直す。`expires` は入れた日の3か月後の同日。**ログ §3 と同じ値にする**

- 効果効能の断定、噂の断定、特定商品・メーカーへの否定の断定（薬機法・CLAUDE.md §11）

### 初回適用時の確認

T10 を初めて記事に入れるときは、凍結していない記事で行い、`pnpm build` 後に `dist/articles/<slug>/index.html` で次を確かめる:

- 話題の H2 が本文と目次（`ArticleToc`）に出ること
- **表示される本文のテキスト**（タグとコメントを除いた文字列）に `trend-topic` が含まれないこと（HTML のソースにコメントの日付が残るのは許容する）
- 本文 lint・ビルドが通ること

## 8. 記録する

実施したら、同じ作業の中で:

1. `docs/CONTENT_IMPROVEMENT_LOG.md` §1 の**先頭**に1行足す（日付・slug・型 `T10`・内容（話題・段階・新規/差し替え/一般化/削除/昇格/延長）・コミット・登録リクエスト＝「未」）
2. §3 を追加・書き換え・削除する（差し替えは行を書き換え、期限切れで削除・一般化したら行を消す。昇格・延長は段階・見直し期限・延長済みを直す）。差し替えも削除もしなかった枠も、話題を確かめたら「最終確認日」を今日にする
3. §4 の種は §3・§6 で回したものを追記し、確かめた種の欄を埋める
4. 見送り・却下された提案は §2 に1行足す（日付・記事・型 `T10`・判断・理由）
5. push とデプロイの完了後は `kura-content-improve` §6-3 と同じ:
   - **IndexNow を送る**（Bing 向け・AI が実行してよい）: `pnpm indexnow -- --url=https://www.kura-select.com/articles/<slug>/`。**`--url=` には必ず絶対 URL を渡す**（Git Bash では `/` 始まりの値がパスに変換されて壊れる。メモリ `feedback_gitbash_regex_file_filter`）。先に末尾に `--dry-run` を付けて送信先を確かめてもよい
   - **GSC の URL 検査で登録リクエスト**（ユーザー作業）をするよう伝える。済んだと言われたらログの「登録リクエスト」を日付に直す
6. 凍結台帳（JSON・メモリ）には書かない（測定しない）

## 9. 提出前のセルフチェック

- [ ] 期限切れ（`期限 <= 今日`）と見直し期限（`見直し期限 <= 確定日`）を先に拾い、マーカーとログ §3 を `--include="*.md"` 付きの grep で突き合わせたか
- [ ] 凍結台帳を JSON とメモリの**両方**と突き合わせたか。noindex・TODO の停止日・進行中の計画書の測定対象・14日以内の実施を外したか

- [ ] 新規・差し替えは5件以内（B 2件・C 1件以内）か。上限を埋めるために条件を緩めていないか
- [ ] 見出し案・本文案に数値（価格・単価・割合・順位・件数）が無いか
- [ ] 承認前に記事を編集していないか

## 10. やらないこと

- 投稿の埋め込み・投稿へのリンク・投稿文の引用
- X での書き込み・反応・フォロー・設定変更、ログイン操作、CAPTCHA の突破
- 1回の実行で X の検索6回以上、新規・差し替え6本以上（B 3本以上・C 2本以上）
- 上限を埋めるために段階の条件を緩める
- FAQ・title・description・商品構成の変更
- 凍結を起こす・凍結台帳への記帳
- 投稿の URL・本文・投稿者をファイルに保存する
- （注記）話題枠のある記事で単独施策（凍結）を始めるときは、その前に枠を一般化か削除しておく（施策を計画する側の手順）
- X のアカウントに警告が出たら、X を情報源から外してユーザーに伝える
