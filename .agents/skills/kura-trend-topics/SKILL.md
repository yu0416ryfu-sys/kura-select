# KuraSelect 話題の点検と T10 の後始末（第10版・縮小）

**2026-11-20 のユーザー決定で縮小した。新しい T10 枠（日付・期限つきの話題の H2）は入れない。** 判断の根拠は `docs/IMPLEMENTATION_PLAN_TREND_TOPICS_2026-11-20_V10.md`（8回の実行で採用3件・3枠とも話題のクエリ0・受け皿が小さい・話題の性質が日用品に合わない）。第9版までの計画書（`IMPLEMENTATION_PLAN_TREND_TOPICS_2026-10-25.md` ほか）は経緯として残す。

このスキルがすることは2つだけ:

| モード | いつ | 中身 |
|---|---|---|
| **① 後始末** | スナップショットの確定日が、ログ §3 の見直し期限以降になったとき／期限（入れた日＋3か月）が来たとき | 有効中の枠を A へ昇格・延長・一般化・削除のどれかに決める（§2） |
| **② 月1回の話題の点検** | 月1回（第1月曜・週次分析の後） | 外の情報源で話題を拾い、**日付も期限も無い保守の加筆案**を最大3件提案して止まる（§3） |

頼まれた内容がどちらか分からなければ、①の対象があれば①から行い、続けて②をするかを聞く。

## 0. 前提の確認（ここを飛ばさない）

1. `docs/CONTENT_IMPROVEMENT_CATALOG.md` と `docs/CONTENT_IMPROVEMENT_LOG.md` があるか確認する。無ければ止まってユーザーに伝える（docs/ は gitignore 済みで、別 PC には無いことがある）
2. `reports/weekly/` の最新の `snapshot-<確定日>.md` の確定日を見る。**確定日が7日より前なら `pnpm weekly:snapshot` の実行を促す**（実行するかはユーザーに聞く）。この確定日を、①の判定と GSC の窓の終端に使う
3. 有効中の枠をマーカーとログ §3 で突き合わせる。**`.md.bak` を拾わないよう `--include` を必ず付ける**。ずれていたら報告の冒頭に書く
   ```bash
   grep -rn --include="*.md" "trend-topic:start" src/content/articles/
   ```
4. 記事を編集する提案をするときは、デプロイ禁止日（`grep -n "禁止日" docs/TODO.md` で全件）と、月曜なら cron の注意（push は 12:00〜13:00 JST を避け、直前に `git pull --rebase`）を報告に書く

## 1. 共通の決まり

- **新しい T10 枠を入れない。** 見出しに日付を書く加筆・`trend-topic` マーカーを新しく付ける加筆・期限つきの加筆をしない
- **数値を書かない**（価格・単価・割合・順位・件数。CLAUDE.md §5.0.1）。売れ行き（「売れている」「人気No.1」「ランキング1位」）も書かない
- 公的機関・メーカーの発表を根拠にするときは、一次情報を本文に1つだけ示す（通常の外部リンク）。炎上・事故・リコール・仕様変更・価格改定の話は一次情報なしで書かない
- 効果効能の断定をしない。公的機関の注意喚起に関わる加筆で、商品の効果（「予防できる」「防げる」）を書かない。「ウイルス」「感染対策」「予防」「防ぐ」を商品と結び付けて書かない
- 価格改定の話では、改定率・価格を書かない、販売価格が上がると言い切らない、買い急ぎ・買いだめを勧めない
- FAQ（frontmatter `faqs[]`）・title・description・商品構成は変えない
- 凍結を起こさない・凍結台帳に書かない（測定しない）
- 投稿の埋め込み・投稿へのリンク・投稿文の引用をしない。投稿の URL・本文・投稿者をファイルに保存しない
- 提案のあと、ユーザーの判断を待たずに記事を編集しない

## 2. ① 後始末（有効中の T10 枠）

### 2-1. 対象

- ログ §3 の行のうち、**期限（入れた日＋3か月）<= 今日** の枠
- ログ §3 の行のうち、**見直し期限 <= スナップショットの確定日** の枠（確定日が届いていない枠は次回に回す）

### 2-2. 見直し期限の判定

ログ §3 の「話題の言葉（表記ゆれ）」を含むクエリの、直近28日（終端＝スナップショットの確定日）の **GSC＋Bing の合計**の表示で決める。

- GSC: `mcp__gsc__gsc_search_analytics` に `dimensions:["query"]`・`filterPage: https://www.kura-select.com/articles/<slug>/`・`rowLimit: 5000`
- Bing: `mcp__bing__bing_page_query_stats` に `page`・`startDate: 確定日−27日`・`endDate: 確定日`・`sortBy: "Impressions"`・`rowLimit: 1000`。`Date` が窓の中の週だけを足し、欠けた週を補わない
- 返った行数が `rowLimit` と同じなら打ち切りの可能性があると報告に書く

| 表示（28日・GSC＋Bing） | 判定 |
|---|---|
| **3以上** | **A に上げる**（マーカーの `tier=A` にし、`review=`・`extended=` を消す。期限は入れた日＋3か月のまま） |
| **1〜2** で未延長 | **見直し期限を4週延ばす**（`extended=1`・`review` を旧見直し期限＋28日。段階は変えない。1回だけ） |
| それ以外（0、または延長済みで2以下） | **一般化するか削除する**（§2-3） |

- 第9版までの延長条件「話題が続いている（トレンド横ばい以上＋X/Yahoo!リアルタイム検索）」は使わない。Google トレンド・X は①では開かない

### 2-3. 期限切れ・一般化・削除

- **一般化を基本にする**: 時期を問わない書き方に直し、`trend-topic` マーカー2行と見出しの「（YYYY年M月時点）」を外す。「〜が話題ですが」「最近〜という声が」などの時期に結び付いた言い回しを、いつ読んでも成り立つ文に直す。公的機関の呼びかけは「〇〇（機関名）は△△を呼びかけています」のように日付に依らない形にする（呼びかけ自体が終わったものは書かない）
- 一般化しても読者に役立たない（その時だけの出来事の話）なら**削除**する（マーカーの範囲をまるごと消す）
- 触るのはマーカーの範囲だけ。既存の本文・見出しは書き換えない
- 枠のある記事が凍結中なら編集しない。その凍結が何を測っているかを先に確かめ（`data/measurement-holds.json` とメモリ `project_measurement_holds`）、区分C に当たるかも含めてユーザーに聞く（CLAUDE.md §5.0.3）。対照群なら解除日まで「凍結のため保留」と書き続ける
- 後始末は14日ルールの対象外（古い日付を残さないことを優先する）

### 2-4. 提案して止まる

```
## T10 の後始末（YYYY-MM-DD）

前提: スナップショット確定日 YYYY-MM-DD ／ マーカーとログ §3 の突き合わせ: ずれなし（あれば内容）

| # | 記事 | 話題 | 見直し or 期限切れ | 話題のクエリの表示（GSC N・Bing M／28日） | 判定（A へ昇格・延長・一般化・削除） | 一般化する場合の書き直し方（要点） |
|---|---|---|---|---|---|---|
```

出したら止まり、ユーザーの判断を待つ。

### 2-5. 実施と記録

1. **1記事1コミット。** 編集の前に記事を Read する
2. `pnpm test` と `pnpm build` を通す（出力が長いのでサブエージェントに任せてよい。メモリ `feedback_token_saving_subagents`）。読者に見える本文を変えたら `pnpm content:stamp` を実行し、`data/content-dates.json` を同じコミットに入れる（A への昇格・延長はマーカーだけなので不要）
3. コミットメッセージは「<slug> の話題枠を一般化」「<slug> の話題枠を削除」「<slug> の話題枠を A に昇格」「<slug> の話題枠の見直し期限を延長」の形
4. ログ §1 の**先頭**に1行足す: 日付・slug・型 `T10`・内容（先頭にラベル `見直し→A` / `見直し→延長` / `見直し→一般化` / `見直し→削除` / `期限切れ→一般化` / `期限切れ→削除` のどれか、続けて段階・種類・話題の言葉）・コミット・登録リクエスト＝「未」
5. ログ §3: A への昇格・延長は段階・見直し期限・延長済みを直す。一般化・削除したら行を消す
6. push はユーザーの指示があってから。push とデプロイの後、`pnpm indexnow -- --url=https://www.kura-select.com/articles/<slug>/`（**絶対 URL**。メモリ `feedback_gitbash_regex_file_filter`）を送り、GSC の URL 検査で登録リクエスト（ユーザー作業）を頼む
7. **ログ §3 の枠がすべて消えたら**、報告に「T10 の枠は残っていない。①の後始末は以後不要」と書き、`docs/TODO.md` の後始末の行を片づけるよう伝える

## 3. ② 月1回の話題の点検

### 3-1. 情報源（読むだけ）

| 情報源 | ブラウザ | 上限 |
|---|---|---|
| 外の情報源 ①〜⑦（下の表） | 内蔵ブラウザ | 合わせて**12ページまで**（一覧から記事・お知らせ・PDF を開くのも1ページ） |
| Yahoo!リアルタイム検索（検索） | 内蔵ブラウザ | **5回まで**。拾った話題が SNS で話題かを確かめるだけ（件数の読み取りは要らない） |
| X の検索（任意） | Claude in Chrome（ユーザーのログイン済み Chrome） | **2回まで**。記事のジャンル語で、SNS だけで広がる話題（小売のセール・使い方の流行）を拾うときだけ。読むだけ（投稿・いいね・リポスト・フォロー・DM・設定変更をしない）。ログインが切れていたら飛ばす |

| # | 情報源 | URL | 見るところ |
|---|---|---|---|
| ① | Yahoo!リアルタイム検索 | `https://search.yahoo.co.jp/realtime` | 「急上昇ワード」「トレンド」の一覧 |
| ② | 消費者庁リコール情報サイト | `https://www.recall.caa.go.jp/` | 「重要なお知らせ」「新規登録情報」（直近1か月）。住居品・保健衛生品・光熱水品など |
| ③ | 厚生労働省 報道発表資料（月別）・感染症情報 | `https://www.mhlw.go.jp/stf/houdou/houdou_list_YYYYMM.html`・`https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/kenkou/kekkaku-kansenshou/index.html` | 日付つきの発表・お知らせ |
| ④ | 気象庁 報道発表資料（年別） | `https://www.jma.go.jp/jma/press/index.html?t=1&y=NN`（NN は令和の年2桁） | 季節の見通し・記録的な天候 |
| ⑤ | Yahoo!ニュース検索 | `https://news.yahoo.co.jp/search?p=価格改定`・`https://news.yahoo.co.jp/search?p=値上げ+日用品` | 直近1か月の記事 |
| ⑥ | PR TIMES「日用品」 | `https://prtimes.jp/topics/keywords/日用品` | リニューアル・容量変更・価格改定・販売終了の発表 |
| ⑦ | 楽天 デイリーランキング（日用品雑貨・文房具・手芸） | `https://ranking.rakuten.co.jp/daily/215783/` | 受け皿の記事のジャンルの商品が目立っていないか |

- 画面を普通に読むだけにする。`fetch`・スクリプトでの一括取得・連続した自動の読み込みをしない
- ログイン・CAPTCHA・429 が出た情報源はその回は止める（別のブラウザで取り直さない）
- ⑦ はランキングに出ているだけ・セールで上がっただけの話題は使わない。⑥ は「発表があった」事実の根拠にだけ使い、商品の良し悪しの根拠にしない
- Google トレンドは使わない（§3-4 の種の確認だけ例外）

### 3-2. 話題を加筆案にする

1. 拾った話題ごとに、**その話題で読者の買い方・使い方が変わる**受け皿の記事を探す（記事の title が答えている問いから外れる話題は使わない）
2. 受け皿を `kura-content-improve` §2 のふるい（凍結・noindex・TODO の停止・進行中の計画書の測定対象・14日以内の実施・§2 で見送り済み・draft）にかける。同じ話題に受け皿が複数あれば、28日クリックが少ない記事を選ぶ（メモリ `feedback_trend_topic_avoid_earning_articles`）
3. 話題を**時期を問わない知識**に置き換え、カタログの型（T1〜T9）のどれで入れるかを決める。例:
   - 公的機関の季節の注意（防災・感染症・大掃除の洗剤の扱い）→ T4（使うときと保管の注意）・T2（失敗例）・T1（よくある疑問に答える H2）
   - メーカーのリニューアル・容量変更・販売終了 → 比較表の商品が対象なら区分C の是正か `kura-article-add` の差し替え候補として報告（T10 では扱わない）
   - 使い方の流行・疑問 → T1・T2
4. **すでに本文に同じ内容があれば提案しない**（Read で確かめる）
5. 話題の需要の判定（段階・トレンドの伸び）はしない。代わりに「その知識が受け皿の記事の読者の判断に効くか」と「一次情報があるか」で選ぶ

### 3-3. 提案して止まる

```
## 月1回の話題の点検（YYYY-MM-DD）

回数: 外の情報源 N/12 ページ ／ Yahoo!リアルタイム検索 N/5 回 ／ X N/2 回（使わなければ 0）

### 加筆案（最大3件・日付と期限は付けない）

| # | 記事 | 拾った話題（情報源・日付） | 型（T1〜T9） | 書く内容（見出し案） | 一次情報 | 注意 |
|---|---|---|---|---|---|---|

拾ったが使わなかった話題: <話題>（理由）…
新規記事の種（§3-4）: 追記 N件・判断を埋めた種 N件
```

- 見出し案に日付・数値・売れ行きが入っていないかを提案の時点で確かめる
- 条件を通った案が無ければ0件で止める。件数を埋めるために条件を緩めない
- 出したら止まり、ユーザーの判断を待つ

### 3-4. 新規記事の種（ログ §4）

- 既存記事に受け皿が無いジャンルの話題は、ログ §4 に「確認待ち」で記録する（初めて見た日・話題（ジャンル語）・情報源）。「受け皿が無い」はサイト全体の query 次元で判断する
- 初めて見た日から14日以上たった種は、次の3点を確かめて「2週後の確認日」「需要の向き」「楽天で同用途5件以上」「判断」を埋める:
  1. Google トレンド（Claude in Chrome・日本・過去90日。季節の語は過去5年で前年同期と比べる）で需要が伸び・横ばい（下降なら見送り）。**1種1語だけ**。429・CAPTCHA が出たら次回に回す
  2. ジャンル語が一般名詞（固有の商品名・流行語は見送り）
  3. 楽天で同じ用途・同じ年齢層の商品が5件以上（メモリ `feedback_no_mixed_use_rankings`）
- 3点を満たした種は「kura-article-recommend へ回す」、満たさなければ「見送り（理由）」

### 3-5. 実施と記録

- 承認された加筆は `kura-content-improve` §5 の 1〜6 に従って実施する（1記事1コミット・Read してから編集・`pnpm test`／`pnpm build`・`pnpm content:stamp`・push はユーザーの指示があってから）
- ログ §1 には**実施した型**（T1〜T9）で書き、内容の先頭に「話題の点検（T10縮小）由来: <話題>」と書く。型は T10 にしない（14日ルールに数える）
- 見送り・却下された案は §2 に1行足す（型は実施しようとした型）
- §4 の種を更新する

## 5. やらないこと

- 新しい T10 枠を入れる（段階 A/B/C・B（事実）・トレンドでの伸びの判定は第10版で廃止）
- 週次での実行（②は月1回）
- 投稿の埋め込み・投稿へのリンク・投稿文の引用、X での書き込み・反応・フォロー・設定変更・ログイン操作・CAPTCHA の突破
- `fetch`・スクリプトでの一括取得、429・CAPTCHA のあとに別のブラウザで取り直すこと
- FAQ・title・description・商品構成の変更、凍結を起こすこと・凍結台帳への記帳
- 投稿の URL・本文・投稿者をファイルに保存すること
- X のアカウントに警告が出たら、X を情報源から外してユーザーに伝える
