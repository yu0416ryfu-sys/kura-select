# 記事の調査・事実照合・作業の分担（共通手順）

`kura-article-create` / `kura-article-add` / `kura-content-improve` が参照する。`kura-index-recover` は §7-1（事実の照合）でこのファイルの §4・§6 を参照する。元は `kura-index-recover` の §5・§6「口コミの書き方」・§9（あちらはスキル内に同じ内容を持つ。この手順を直すときは両方を見る）。

**トークン節約は「読まない」ではなく「収集をサブエージェントに任せる」で取る。** 本体は判断・執筆・是正だけを行い、商品ページやレビューの長文は本体のコンテキストに入れない。

## 1. どの担当にも必ず伝えること

- 本番のページ（`www.kura-select.com`）をブラウザで開かない（GA4 に混入する）。確認は localhost か `curl`
- アフィリエイトリンク（`hb.afl.rakuten.co.jp`）を踏まない（自己クリックになる）。`pc=` をデコードした `item.rakuten.co.jp` の URL を開く
- 楽天を WebFetch で読まない（文字化けで誤読する。メモリ `reference_rakuten_item_page_reading`）。ブラウザで開き、`document.body.innerText` から読む
- ブラウザが使えないときは WebFetch に切り替えず、止まって本体に報告する

## 2. 収集（サブエージェント・sonnet）

収集だけを任せる。何を書くか・書かないかの判断はさせない。

| 対象 | 読むところ |
|---|---|
| 商品ページ | 商品名・ブランド・容量とセット構成・商品区分（化粧品／医薬部外品など）・成分・使用方法・使えない条件（素材・設備・年齢など） |
| 口コミ | 楽天レビューの星1〜3と星5を商品ごとに読み、テーマ（使い心地・失敗・届き方など）ごとの傾向にまとめる。投稿文は原文の抜き出しとして収集ファイルに残すだけで、本文には引用しない |
| 一次情報 | メーカー・業界団体・公的機関のページから、本文の断定に使う事実（表示の決まり・使い方・安全上の注意） |

- 回数や日数は、商品名の「〇回分」ではなく使用方法の量で計算する
- 商品が多いときは4〜5件ずつに分け、2〜3体を並列に走らせる
- **出力は1ファイル**: スクラッチパッドに `research-<slug>.md`。商品ごと・出典ごとに節を分け、**各事実に URL と該当箇所の原文**を付ける。読めなかったページは「未取得（理由）」と書く
- 本体は要約だけを受け取り、書く段で必要な節だけをファイルから読む

## 3. 書くときの共通ルール

- 本文・商品説明・FAQ に書く事実は、収集ファイルにあるものだけにする。無い事実は書かないか、収集をやり直す
- 価格・単価・レビュー件数・順位を本文と `faqs[].answer` に書かない（CLAUDE.md §5.0.1）。効果効能を断定しない。「最安」「No.1」は根拠が無ければ書かない（§11）
- 本文の太字は、閉じる `**` の直前が約物なら `<strong>`（メモリ `feedback_markdown_bold_cjk`）。`faqs[].answer` は `**` のまま

### 口コミの書き方

読んだ日と範囲を本文に書く。投稿文を引用せず、「〜という声がありました」の傾向にまとめる。評価点とレビュー件数の数値は書かない。効果の断定になる声は載せない。特定商品の欠点として断定しない。

## 4. 事実の照合（別のサブエージェント・sonnet 以上）

本文を書いていない担当に任せる。照合する担当は記事を編集しない。依頼文は §6 の照合の雛形を使う。

- 渡すもの: 記事ファイルのパスと照合する範囲（新規なら全体、加筆・商品の追加なら足した節と、追加・直した商品）、収集ファイルのパス。**依頼する側が心配な箇所（「特に〇〇を見て」）は書かない**（照合がそこに寄り、ほかを見なくなる）
- 読む順番（2段。入れ替えない）:
  1. **収集ファイルを開く前に**、照合する範囲だけを読み、確かめるべき断定を一覧に書き出す。読者や詳しい人が疑いそうなもの（商品の区分・成分・使えない条件や設備・互換・安全・数値と計算・効果をうたう表現）を優先する
  2. そのあとで収集ファイルと記事の `products[]` を開き、一覧の各項目を、収集ファイルの要約ではなく**各事実に付いた原文**と突き合わせる（§2 で原文の添付は必須）。原文がその断定を支えていなければ、要約に書かれていても「根拠なし」とする。商品の断定では、原文に書かれた商品名・URL が、記事の `products[].name`・`rakutenUrl`（`pc=` をデコードした `item.rakuten.co.jp` の URL）と同じ商品かも確かめる（別の商品のページを読んだ取り違えを拾う）。照合する担当は出典のページを開き直さない（集め直すかは本体が決める）
- 確かめること（優先順）: 商品に関する記述（区分・成分・使えない条件・`features` / `pros` / `cons` / `recommendedFor`）／数値と計算／薬機法・景表法に触れる表現／本文に出る銘柄が `products[]` に実在するか／収集ファイルに根拠の無い断定
- 返させるもの: 書き出した断定の件数（合った件数・根拠なしの件数）と、指摘の一覧（箇所・何が違うか・根拠の URL と原文）。問題が無い項目は書かせない
- 本体が指摘を直す。「根拠なし」の断定は、集め直して根拠を付けるか、断定を外す。直した点と直さなかった点（理由つき）を報告に書く

## 5. 分担の表

| 作業 | 担当 |
|---|---|
| 楽天の商品ページとレビューの収集、メーカー・公的機関の資料の抜き出し | sonnet。URL と原文の添付を必須にする |
| `pnpm test` / `pnpm build` / `pnpm check-internal-links` / デプロイの確認 | haiku か sonnet。要点だけ報告させる |
| 事実の照合 | 本文を書いていない別のサブエージェント（sonnet 以上） |
| 判定、疑問リスト、構成、本文、図解、商品説明、是正の判断 | 本体 |

## 6. 依頼文の雛形

収集の依頼（§2）:

```text
KuraSelect の <slug> の記事のために、次の楽天商品の情報を集めてください。判断や執筆はしないでください。
守ること: 本番の kura-select.com を開かない／hb.afl.rakuten.co.jp のリンクを踏まない／楽天を WebFetch で読まない（ブラウザで開き document.body.innerText から読む）。ブラウザが使えなければ止まって報告。
商品: <rank・name・item.rakuten.co.jp の URL の一覧>
読むところ: 商品名・ブランド・容量とセット構成・商品区分・成分・使用方法・使えない条件、レビューの星1〜3と星5の傾向
出力: <スクラッチパッドの絶対パス>/research-<slug>.md に、商品ごとの節で、各事実に URL と原文を付けて書く。読めなかったものは「未取得（理由）」。
返答: ファイルのパスと、商品ごとに3行以内の要約だけ。
```

照合の依頼（§4）:

```text
KuraSelect の <slug> の記事の事実を照合してください。記事は編集しないでください。
守ること: 本番の kura-select.com を開かない／hb.afl.rakuten.co.jp のリンクを踏まない／楽天を WebFetch で読まない。
記事: <記事ファイルの絶対パス>／照合する範囲: <全体、または足した節の見出しと、追加・直した商品の rank>
収集ファイル: <収集ファイルの絶対パス（§6 の収集の雛形なら <スクラッチパッドの絶対パス>/research-<slug>.md）>
手順: ① 収集ファイルを開く前に、照合する範囲だけを読み、確かめるべき断定を一覧に書き出す（商品の区分・成分・使えない条件や設備・互換・安全・数値と計算・効果をうたう表現を優先）。② そのあとで収集ファイルと記事の products[] を開き、一覧の各項目を、収集ファイルの要約ではなく各事実に付いた原文と突き合わせる。原文がその断定を支えていなければ「根拠なし」とする。商品の断定では、原文の商品名・URL が記事の products[] の name・rakutenUrl（pc= をデコードした URL）と同じ商品かも確かめる。出典のページは開き直さない。
返答: 書き出した断定の件数・合った件数・根拠なしの件数と、指摘の一覧（箇所・何が違うか・根拠の URL と原文）。問題の無い項目は書かない。
```
