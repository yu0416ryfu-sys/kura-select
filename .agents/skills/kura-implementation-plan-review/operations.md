# 呼び出す側の運用（レビュー担当は読まなくてよい）

計画書の作成者（呼び出す側）が守ること。

## 呼び方

- 作成者と別のコンテキスト（サブエージェントか新しいチャット）で呼ぶ。テンプレ全体に効くものは Codex にも見せる
- **渡すのは、計画書のパスと「初回か再レビューか」と、再レビューなら前回の指摘ファイルのパスだけ。** 例外として、第0巡で「価値なし」と出た計画をユーザーが実施すると決めたときだけ「価値レビュー省略」を添える（ユーザーの決定をレビュー履歴に書いてから）。 「特に〇〇を見て」など作成者の心配ごとをプロンプトに書かない。心配ごとは別紙 `<計画書名>.notes.md` の「作成者が迷っている点」の節に書く（第2巡で読まれる）。作成スキル（`kura-script-impl-plan`）は別紙を作る。作成スキルを使わずに書いた計画書では、作成者が手で別紙を作る（本体の末尾に置く旧形式もレビューできるが、本体を丸ごと読まれると目に入る）
- 再レビューは、前回と同じエージェントの続きではなく、新しいコンテキストで呼ぶ
- 分冊は一度に渡す（読む順番はスキルが守る）。分冊を後から渡す2段方式（この計画書で使った形）を使うときだけ、同じ回の第1段・第2段を同じエージェントの続きにしてよい

### 呼ぶときのプロンプト（このまま使う）

計画書のパスと回だけを差し替える。分冊なら「計画書:」に全部のパスを並べる。別紙（`.notes.md`）のパスは渡さない（スキルが名前から見つける）。「参照ファイルも読んで」「特に〇〇を見て」は足さない。足してよい禁止は「本番を開かない」「リンクを踏まない」「ファイルを編集しない」の3つだけ（テンプレの最後の行が3つ目にあたる）。

Claude Code（サブエージェント）:

```
作業ディレクトリは C:\Projects\KuraSelect。Skill ツールでスキル `kura-implementation-plan-review` を呼び、その本文の手順どおりにレビューしてください。スキルのディレクトリのほかのファイルは、本文が指す巡になってから開いてください。

- 計画書: <本体のパス>
- 初回（再レビューなら「再レビュー・前回の指摘: <パス>」）

ファイルの編集はしないでください。返答はスキルが定める形式で。
```

Codex: 1行目を「`.agents/skills/kura-implementation-plan-review/SKILL.md` だけを読み、その手順どおりにレビューしてください。同じディレクトリのほかのファイルは、本文が指す巡になってから開いてください。」に替える。

## 前回の指摘ファイル

- 前回の返答はプロンプトに貼らず、ファイルに保存してそのパスを渡す
- 名前は計画書の名前から `.md` を除き `.review-<回>.md` を付ける（例: `docs/IMPLEMENTATION_PLAN_FOO_2026-11-18.review-1.md`）。分冊は PART1 の名前を基準にする（例: `..._PART1.review-1.md`）。同じ回に Codex にも見せたら `.review-1-codex.md` と担当名を付ける

## 往復と終え方

- 第0巡が「価値なし」なら、計画書を直して再レビューに回さない。結論と代わりの案をユーザーに見せ、実装しない／縮小して書き直す／そのまま実施（「価値レビュー省略」で呼び直す）のどれにするかを決めてもらう
- 第0巡が「価値が薄い」なら、技術の指摘が片付いても、実装の前に代わりの案と並べてユーザーに実施するかを確かめる
- 往復は既定で最大2回。ユーザーが回数を指定したらそれに従う
- 終えてよいのは、blocking が 0 で、major をすべて直したか、直さない理由をレビュー履歴に書いたとき
- 上限に達して blocking が残ったら、残りを一覧にしてユーザーに判断を求める
- 再レビューを省いてよいのは、変更範囲を広げず節を外すだけの改訂で、外した節が受入確認・ロールバック・測定窓の節ではないとき。外した節番号を grep して参照の残りが0件であることを確かめ、その結果と省いた理由をレビュー履歴に書く

## レビュー履歴

別紙 `.notes.md` の「レビュー履歴」の節（旧形式は計画書の同じ節）に、次の表で追記する。

| 回 | 日付 | 担当 | 価値 | blocking | major | minor | 第1巡 / 第2巡 | 第1巡の指摘の観点 | 主な指摘と対応（直した節） |
|---|---|---|---|---|---|---|---|---|---|

- 「価値」は第0巡の判定（`あり`・`薄い`・`なし`・`初回で済み`・`省略`）。`なし` のまま実施するなら、ユーザーの決定と日付を「主な指摘と対応」に書く

- 「第1巡の指摘の観点」は、返答の各指摘の「観点」欄（`L8.1` や `新規: 名前`）をそのまま並べる
- 直さない指摘は、ID と理由を「主な指摘と対応」に書く（次の回の第3巡で `不採用（理由あり）` になる）

## `checklist.md` の育て方

- 同じ `新規:` の観点が、2つ以上の計画書で第1巡に出たら、`checklist.md` に足す候補にする
- 長く一度も指摘に結びつかない観点は削る候補にする
- 足す・削るはユーザーに確かめてから行う

## 読んだ順番の確かめ方

- 受入のとき、またはレビューが前回の指摘や分冊に引きずられていると疑うときに、呼び出す側がサブエージェントの transcript（`~/.claude/projects/<プロジェクト>/<セッション>/subagents/agent-<id>.jsonl`）のツール呼び出し順で確かめる。見るのは、`round2/checklist.md`・別紙・ほかの分冊・前回の指摘ファイルを開いたのが第1巡の調べの後か、の1点。Read だけでなく、Bash の `cat`・`sed` でまとめて開いた呼び出しも、コマンドに含まれるファイル名で数える。旧形式の計画書なら、本体を範囲なしで読んでいないかも見る
- サブエージェントの思考は transcript では伏せられていることが多いので、「書き出してから読んだか」は返答の第1巡の指摘と、読んだ順番で判断する
