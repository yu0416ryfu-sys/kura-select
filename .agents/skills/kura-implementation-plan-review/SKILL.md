# KuraSelect 実装計画レビュー

実装計画書を、実装前に「やる価値があるか」と「破綻しないか」の2つで確認する。価値の判定（第0巡）は技術の整合より先に行い、結論ではこちらを優先する。長い説明よりも、現行コード・運用ルールと噛み合わない点を短く、根拠つきで指摘する。呼び出す側の決まりは同じディレクトリの `operations.md` にある（レビュー担当は読まなくてよい）。

## 0. 前提

- 作成者と別のコンテキストで実行する。**この会話の中で対象の計画書を書いた・直したなら、レビューせずに「別のコンテキスト（サブエージェントか新しいチャット）で呼び直してほしい」とだけ返して止まる**
- **計画書もコードも書き換えない。** 指摘を返すだけにする。反映とレビュー履歴の追記は作成者側が行う
- 始める前に `git status --porcelain` を取っておく（返答の最後で比べる）
- 実行してよいのは読むだけのコマンド: grep・find・ls・wc・diff・`sed -n`・ファイルを読むだけの `node`・`git log` / `git diff` / `git show` / `git status`・`pnpm test`・`pnpm search-status -- --offline`（保存分だけを読む。`--offline` なしは `data/google-search-status.json` を書き換える）。ファイルを書く・外部に送るコマンドは実行しない: `:dry` の script（外部 API を叩き、`reports/` に書き出すものがある）・`pnpm build`・write 系・commit / push。比べるための一時ファイルも書かない（`diff <(…) <(…)` を使う）
- 推測で指摘しない。指摘には、読んだファイルと行（または grep の結果）を根拠として添える。確かめられなかったことは「未確認」と書く
- **先入観を入れない順番で読む。** 観点表（`checklist.md`）・前回の指摘・作成者の心配ごとを先に読むと、そこに書かれたことしか探さなくなる。§2 の順番を守る

## 1. 対象を決める

- **版**: ファイル名の `_V8`・`_V9` や本文中の「第N版」で版が複数あるときは、指定された版を使う。指定がなければ最新の版を対象にする。`_V9` と `_V10` は数値で比べる（ファイル名の並び順で決めない）。日付だけが違うファイル（`_2026-10-25_V8` と `_2026-10-27_V9` など）も、日付より前の名前が同じなら同じ計画の版とみなす
- **分冊**: `_PART1`・`_PART2` や別紙に分かれているときは全部を対象にする。本体は `_PART1`（無ければ番号の無いファイル）。第1巡で読むのは本体だけで、ほかの分冊（根拠・採否・作成者の迷い）は第2巡で全部読む
- どの版・どのファイルを見たかを返答の冒頭に書く

## 2. 進め方（第0巡＋3巡）

### 第0巡: 価値レビュー（初回は必須）

KuraSelect はアフィリエイトサイトで、作業時間の本業は記事・商品・送客。技術的に正しくても、効き目が費用に見合わない計画は実装しない方がよい。この巡では実装の細部（変更ファイル・コード）を読まず、目的と効き目の見込みだけで判定する。

読むもの:
1. 計画書の目的・背景・期待する効果・変更範囲の節（第1巡と同じく、レビュー履歴・作成者の迷い・版の差分の節は飛ばす）
2. 効き目の規模を測るための実績（読むだけ。新たに API を叩かない）: 最新の `reports/weekly/snapshot-*.md`、`reports/affiliate-performance-log.md` の直近の行、ファイル名の日付が最新の `docs/ACCESS_ANALYSIS_*.md`。対象が特定の記事なら、その記事の行だけ拾う
3. メモリ `project_seo_lessons`・`project_*_rejected`・`feedback_value_over_effect_content`・`feedback_no_net_negative_changes`（読めない環境では「メモリ未確認」と書く）

確かめること:
1. **何に効くか**。次のどれに、どの経路で効くかを1行で書く。どれにも効かなければ「なし」
   - 収益: 検索の表示・順位・CTR → 記事の閲覧 → CTA のクリック → 楽天などの成果（どの段に効くか）
   - 読者: 商品選びの役に立つ・誤りを減らす・信頼を上げる
   - 運用: 手作業や判定の手間を減らす・誤判定や事故を防ぐ（月に何分か・どの事故か）
   - 守り: 法務・ASP の規約・リンク切れ・表示崩れへの対応
2. **規模**。対象ページの表示・クリック・送客、または運用で減る手間を、上の実績から数字で見積もる。数字が取れなければ「見込み不明」と書く（推測で埋めない）
3. **費用**。実装とレビュー往復の工数、増える保守（新しいスクリプト・台帳・手順）、本番のリスク（CWV・広告の停止条件・SEO の変動）、機会費用（凍結・デプロイ禁止日・新規記事の枠を食うか）
4. **代わりの案**。何もしなかったときに失うもの。同じ効き目を得られる、もっと小さい案
5. **過去の教訓・没案との重なり**。没にした案を新しい根拠なしに出し直していないか

判定（1つ選ぶ）:
- **なし**: どれにも効かない／費用が効き目を明らかに上回る／没案の出し直しで新しい根拠が無い／差し引きでマイナスになる
- **薄い**: 効くが規模が小さい、または見込み不明で、もっと小さい代わりの案がある
- **あり**: 上のどちらでもない

注意:
- 収益の見込みだけで「なし」にしない。読者の役に立つこと・運用の事故を防ぐことも、独立した価値として数える（メモリ `feedback_value_over_effect_content`）
- 計画書に効き目の見込み（何に・どれくらい）が書かれていないこと自体は、major として第1巡の指摘に入れる（観点 `新規: 効き目の見込みなし`）
- 最終判断はユーザーが行う。レビューは推奨を出すだけ
- **判定が「なし」なら、第1巡以降を行わずに止まる**（§4 の「価値なし」の結論で返す）。ユーザーが実施を決めた計画は、呼び出す側が「価値レビュー省略」と渡す。そのときは第0巡を飛ばし、返答に「第0巡: ユーザー判断で省略」と書く
- 再レビューでは第0巡を省き「第0巡: 初回で済み」と書く。ただし第3巡で計画の目的・変更範囲が初回から変わったと分かったら、最後に第0巡をやり直す

### 第1巡: 自由レビュー

読むもの:
1. 計画書。先に `^#` を grep して見出しと行番号を取る。**grep は本体1ファイルのパスだけに対して行う**（glob を使わない。前回の指摘ファイルやほかの分冊も同じ接頭辞を持つ）。次の節を飛ばして、行範囲を指定して読む（Claude Code は Read の `offset` と `limit`、Codex は `sed -n`。範囲を省くとファイルの末尾まで読み込まれ、飛ばす節も目に入る）: レビュー履歴・レビューの反映・セルフレビュー・作成者が迷っている点・版の差分や変更点（節名が違っても、過去の指摘や作成者の懸念を書いた節）。**飛ばす節はコードフェンスの外の見出しだけで決める**（フェンスの中はレビューする本文なので読む）。迷ったら読む。本文中の「（B3 反映）」のような注記は避けられないので、目に入っても探す範囲をそこに寄せない
2. 計画書が変更対象に挙げたファイルの、変更箇所とその前後
3. 計画書が参照する関数・型・定数・script 名・ファイル・スキル名・節番号・行番号の実在（名前が合っているかだけ）。確認コマンドがあれば `package.json` の scripts
4. **grep で影響先を探す（必須）**: 計画が変える関数・型・CSS トークン・コンポーネント・スキル名・節番号を grep し、計画に挙がっていない参照元が無いか確かめる。除外: `node_modules`・`dist`・`.astro`・`.claude/worktrees/`（古いコピー）・`docs/*.review-*.md`（前回の指摘）・対象の計画書のほかの分冊。`docs/` のほかの計画書は、名前の実在を確かめるのに使うだけにする。見つかった参照元は該当行の前後だけ読む。ヒットが30件を超えたら全部は読まず、ディレクトリ別の件数を根拠として書く

やること: 観点表を使わず、「この計画どおりに実装・デプロイしたら何が壊れるか、何が判定できなくなるか」を探す。**第1巡の指摘を見出しの1行ずつでも書き出してから**、`checklist.md` を読む（返答では第1巡の指摘として残る）。第1巡の指摘は第2巡で消さない（重大度を変えるのはよい）。誤りと分かったものは消さずに `取り下げ` に移す（§4）。

### 第2巡: 観点表

1. 同じディレクトリの `checklist.md` を読み、計画の種類を判定して、当てはまる観点を当てる。種類別に読むファイル（凍結台帳など）も `checklist.md` に従う。**軽い計画**（S だけで本番に出ない）は、`checklist.md` の §2 の S・§3・§4・§9 だけを当てればよい
2. 第1巡で飛ばした節とほかの分冊を読み、作成者の問いに答える（返答の「作成者の問いへの回答」に書く）。作成者の迷いの節が無い計画書では、返答に「作成者の迷いの節なし」と書く
3. 第1巡と重ならない指摘だけを足す

### 第3巡: 前回の指摘（再レビューのときだけ）

1. 前回の指摘（呼び出し側が渡したファイル）と、計画書のレビュー履歴の節を読む
2. 前回の指摘を ID ごとに確かめ、`解消`・`部分解消`・`未解消`・`不採用（理由あり）` を付けて一覧にする。`不採用` は作成者が履歴に理由を書いて直さなかったもの。`docs/` は git 管理外で版の差分が取れないので、指摘ごとに該当箇所を読み直す。解消済みの内容は再説明しない
3. **前回不採用の指摘**: 第1巡・第2巡に同じ指摘が出ていたら、その理由に反論できるときだけ残し、反論を1行書く。反論できなければ `取り下げ` に移す
4. 第1巡・第2巡の指摘のうち、前回の指摘の修正で生じたものには「前回の M2 の修正で生じた」のように書き添える。修正で過剰に複雑になった箇所も指摘する。第3巡で新しく見つけた指摘は、見出しの末尾を「第3巡」にする

**読まない**: `node_modules`・`dist`・`.astro`・`.claude/worktrees/`。`dist/` の確認は実装後の受入で行うものなので、計画書の受入にその手順があるかだけを見る。

## 3. 重大度

| 重大度 | 定義 |
|---|---|
| blocking | このまま実装すると壊れる・必ず落ちる・判定できない・プロジェクトのルールに反する |
| major | 実装はできるが、手戻り・誤判定・影響範囲の見落としが起きやすい |
| minor | 説明の粒度・保守性・言い回し |

blocking の具体例は `checklist.md` の末尾にある（第2巡で読む）。major は、直すか、直さない理由をレビュー履歴に書くまで残る。

## 4. 返答の形

冒頭に1行: 対象の計画書と版（分冊ならファイル全部）、当てはめた種類、件数（`blocking N / major N / minor N`）、巡ごとの件数（`第1巡 N / 第2巡 N`、再レビューでは `/ 第3巡 N` も）。

その次に第0巡の結果を置く:

```
価値: あり｜薄い｜なし（または「第0巡: 初回で済み」「第0巡: ユーザー判断で省略」）
- 効く先: 収益（どの段）／読者／運用／守り。経路を1行
- 規模: 数字と出典（取れなければ「見込み不明」）
- 費用: 1行
- 代わりの案: 1行（薄い・なしのときは必須）
```

再レビューでは、その次に第3巡の一覧（前回の指摘の ID と状態）を置く。

指摘は第1巡と第2巡を混ぜて重大度の順に並べ、1件ずつ次の形で書く。見出しの先頭に ID（blocking は `B1`、major は `M1`、minor は `m1` から通し番号）、末尾に見つけた巡を書く。minor は本文つきで5件まで。超えた分は見出しの1行だけ並べる（巡ごとの件数には含める）。

```
### B1 [blocking] 短い見出し（第1巡）
- 場所: 計画書 §N（行）／対象ファイル:行
- 問題: 何が噛み合わないか
- 根拠: 読んだコード・grep の結果（1〜2行）
- 直し方: 1行（案が無ければ「要相談」）
- 観点: checklist.md の節番号に `L` を付けたもの（例: `L8.1`）。どれにも当たらなければ `新規: 短い名前`
```

指摘の後に、当てはまるものだけ置く:
- `取り下げ`: 第2巡・第3巡で取り下げた指摘（ID・見出し・理由1行。件数には数えない）
- `作成者の問いへの回答`: 問いの番号ごとに1行（節が無ければ「作成者の迷いの節なし」）

最後に結論を1行と、`git status --porcelain` を始める前と比べた結果（同じなら「作業ツリーの変化なし」）を書く。結論は次のどれか（価値の判定が指摘の件数より優先する）:
- 価値なし: 「実装しない（推奨）。続けるかはユーザー判断（続けるなら呼び出し側が「価値レビュー省略」を付けて呼び直す）」。第1巡以降は行っていないので、冒頭の件数は書かない
- 価値が薄い: 下の3つのどれかの頭に「価値が薄いので、代わりの案と比べて実施するかをユーザーに確かめてから」を付ける
- blocking 0・major 0: 「実装に進めてよい」
- blocking 0・major あり: 「major を直すか、直さない理由をレビュー履歴に書いてから実装に進めてよい」
- blocking あり: 「blocking を直して再レビュー」

問題が無いとき:

```
対象: docs/IMPLEMENTATION_PLAN_XXX.md（第2版）／種類: T・D
blocking 0 / major 0 / minor 2（第1巡 1 / 第2巡 1）
価値: あり
- 効く先: 運用（月次の手作業を削る）
- 規模: 月1回 × 30分（docs/TODO.md の手順から）
- 費用: スクリプト1本とテスト
### m1 [minor] …（第1巡）
実装に進めてよい。作業ツリーの変化なし。
```
