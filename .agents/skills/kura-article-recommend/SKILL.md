# KuraSelect 記事候補提案スキル

KuraSelectの新規比較記事候補を、思いつきではなく既存コンテンツとRAG/MCP情報に基づいて提案する。候補出しだけを扱い、記事ファイル作成は `kura-article-create` に引き継ぐ。

## 参照順

1. `src/content/articles/` と `src/content/categories/` で既存記事・カテゴリの重複を確認する。
2. `data/rag/summary.json` で記事数・商品数・RAG生成状況を確認する。
3. 必要な範囲で `data/rag/products.jsonl` / `category-rules.jsonl` / `match-decisions.jsonl` / `capacity-patterns.jsonl` を検索する。
4. MCPが利用可能なら、読み取り専用の `kura-content` MCP で `search_rag` / `get_product_context` / `read_latest_reports` を使う。MCPが使えない場合は、その旨をユーザーへ簡潔に報告してからローカルファイルを直接読む。`search_rag` は部分一致検索のため、返却された record の `category` / `articleFile` を確認し、無関係な行が混ざっていないかチェックすること。
5. `reports/addition-candidates-*.md` / `reports/addition-urls-*.md` / `reports/toAI/` は最新または関連ジャンルだけを確認する。`reports/` はコミット対象外なので編集しない。
6. **GSC で需要を実測する。** `mcp__gsc__gsc_search_analytics` を `dimensions:["query"]`・`rowLimit: 5000`・直近28日で投げ（既定の100行だと少ない表示のクエリが落ちる。返った行が5000ちょうどなら打ち切りの可能性を提案に書く）、候補ジャンルの指名クエリが既存記事で表示を拾っているかを見る（窓の終端は `dimensions:["date"]` で実測した確定日まで。CLAUDE.md §5.0.2 のルール1）。最新の `reports/gsc-harvest/harvest-*.md` があれば先に読む。
7. `docs/CONTENT_IMPROVEMENT_LOG.md` §4（新規記事の種）で判断が「kura-article-recommend へ回す」の種を見る（`kura-trend-topics` が記録する SNS・世間の話題由来のジャンル）。**既存の採択基準（vs 記事の2条件・vs 以外は表示30以上・受け皿が無ければ0扱い）と月の新規枠はそのまま適用し、種であることを理由に基準を緩めない。** 受け皿の無い話題は表示が立たず本線では見送りになるのが普通で、種は需要が育ったジャンルを見逃さないための記録にすぎない。本線で落ちた種は、下の「試験枠」の条件で別に評価してよい（試験枠の条件も緩めない）。docs/ が無い環境（別 PC）では飛ばしてよい。

## vs 記事（ブランド一騎打ち）の採択基準（必須）

vs 記事は次の2条件を**両方**満たすときだけ提案する（2026-08 の成功2/失敗2 で完全に分離した基準）。

1. **指名クエリの表示が直近28日で100以上**あること
2. **その表示の主力が選択系クエリ**（`どっち` / `比較` / `どっちが安い`）であること。**情報系**（`違い` / `成分` / `〜とは`）が主力なら作らない

- 情報系が主力だと 10位前後に固定されスニペットで答えが完結し、収益にも遠い（oxiclean-vs-percarbonate は 507表示で①を満たしたのに CTR 0.39%）
- 既存の勝ち記事が同じクエリ群を既に受けている場合はカニバリになるので見送る（無香空間 vs イオン消臭プラスを 2026-08-26 に見送り）
- 一般名詞の新規カテゴリ記事は表示すら立たないことがある（deodorizing-bag）。候補の比較では「指名クエリの受け皿が実測できているか」を優先度の上位に置く

## vs 以外の比較記事の採択基準（必須・2026-10-13）

次の測り方で**表示30以上**のときだけ提案する（様子見の値。見直しは入れ替えログの2週判定を根拠にするときだけ）。

- `mcp__gsc__gsc_search_analytics` を `dimensions:["query"]`（page は使わない）・`rowLimit: 5000`・確定日（`dimensions:["date"]` で実測）までの28日で取る
- **テーマ語と選択系語（`おすすめ` / `比較` / `安い` / `まとめ買い` / `どっち` / `ランキング`）を両方含むクエリの表示を合計**する。テーマ語の表記ゆれ（カタカナ・ひらがな・略称）は候補ごとに列挙し、提案に記録する
- 受け皿になる既存ページが無く表示が測れない題材は **0 として扱い採らない**（deodorizing-bag は確認せずに作り、32日で表示32・クリック0）

## 月の新規枠（入れ替え運用・2026-10-13）

- 新規記事は**暦月で10本まで**、noindex で外した記事と **1対1** で入れ替える。月の枠 ＝ min(10 − その月に公開済みの本数, 累計で外した本数 − 累計の新規本数)（起算日 10-13）
- **枠は `docs/TODO.md` の「入れ替えログ」で確認し、枠を超えて提案しない。** 枠が0なら候補は出さずにその旨を返す
- 基準（vs 記事の2条件・vs 以外の表示30）を通った候補が枠より少なければ、本線はそこで止める。本数を埋めるために基準を緩めない（残った枠は下の「試験枠」の条件だけで扱う）
- 基準を通った候補は**期待送客**（想定表示/日 × 想定 CTR × 型別の送客率）の高い順に並べる。型別の送客率の初期値は vs 記事 4.8%・比較記事 14.6%・まとめ買い型の上位 20〜28%（`docs/REVENUE_REVIEW_2026-10-13.md` §2.3）
- 運用の詳細は `docs/IMPLEMENTATION_PLAN_ARTICLE_ROTATION_2026-10-13.md` とメモリ `feedback_article_rotation`

## 試験枠（外の数字で採る・2026-10-25）

GSC は、書く前の題材ではクエリの表示が立たず、少ない表示のクエリは匿名化で落ちる。上の基準（本線）だけでは受け皿の無いジャンルを構造的に拾えず、月の枠が余り続ける。入れ替えは表示10未満の記事を外した分だけ入れるので、余った枠を使っても失うものは小さい。そこで本線で余った枠の一部を、GSC 以外の数字で採る。

- **本線が先。** 本線を通った候補で枠を使い、残った枠のうち**月2本まで**を試験枠にする。枠が0なら試験枠も出さない
- 次の5つを**すべて**満たす候補だけを試験枠に入れる
  1. **Google トレンドで横ばい以上**: 日本・過去90日（季節の語は過去5年で前年同期と比べる）。テーマ語を**1語ずつ**測る（複数語を並べない）。「データ不足」・過去90日の3分の2以上の点が0なら不可。Claude in Chrome で画面を普通に読むだけ・1回10語まで・429・CAPTCHA が出たら止める（別のブラウザで取り直さない）
  2. **楽天で同じ用途の商品が5件以上**あり、容量・単価・タイプなどで比較表を組める
  3. **買う前に選ぶ題材**: 消耗品・まとめ買い・リピート購入のどれかで、選択系クエリ（おすすめ・比較・安い）で探される。情報系（違い・成分・〜とは）が主の題材は不可
  4. **一般名詞1語だけの広い題材ではない**（用途・対象・規格で絞れている。deodorizing-bag は表示すら立たなかった）
  5. **既存の集客記事と取り合わない**: 本線と同じ GSC の取り方（`rowLimit: 5000`）で、テーマ語を含むクエリを既存記事が28日でクリック1以上取っていたら不可（新規ではなく `kura-content-improve` の加筆に回す）
- 並べ順: トレンドが伸び → 横ばいの順、同じなら楽天の商品数が多い順（想定表示が無いので期待送客は出さない）
- 提案では**「試験枠」と明記**し、本線の候補と混ぜない。採択基準の欄には「トレンドで測った語と向き・楽天の商品数・取り合いの確認結果」を書く
- 公開後は本線と同じく両台帳へ記帳し、**公開2週後の順位帯**で判定して `docs/TODO.md` の入れ替えログに記入する（型の欄に「（試験枠）」）。外すかどうかは通常の月次規則（公開60日以上・表示10未満）で扱い、試験枠だけの特例は作らない
- 試験枠の2週判定が**6本**たまったら、本線と比べた結果をユーザーに示し、試験枠の条件と本線の基準（表示30）を見直すか判断してもらう

## 評価軸

各候補を次の観点で評価する。

- 既存記事との距離: 既存カテゴリに自然につながるか、重複しないか。
- 楽天商品候補の拾いやすさ: 既存RAG・追加候補・カテゴリルールから商品数を見込めるか。
- 比較軸の作りやすさ: 容量、単価、タイプ、素材、用途、対応機種などを比較表に落とせるか。
- 収益性: 消耗品・まとめ買い・リピート購入・単価の高さのいずれかがあるか。**情報系クエリ（違い・成分・〜とは）で集客する記事は収益に遠い**ので、購買直前の選択系クエリを受けられるかで評価する。
- 検索需要の実測: GSC で指名クエリ・選択系クエリの表示が確認できるか（推測だけで需要ありとしない）。試験枠の候補は GSC の代わりに Google トレンドの向きで見る。
- 法務/表現リスク: 薬機法・景表法に触れやすい断定や効果効能訴求が中心にならないか。

## 提案フォーマット

候補は優先順位順に3〜8件へ絞る（ただし月の新規枠と、基準を通った本数を超えない）。各候補に以下を短く添える。

```text
1. 記事テーマ
   - 枠: （本線 / 試験枠）
   - 採択基準: （vs 記事: 指名クエリ表示と主力クエリ / vs 以外: 測ったクエリの表記ゆれと表示合計 / 試験枠: トレンドで測った語と向き・楽天の商品数・取り合いの確認結果）
   - 期待送客: （想定表示/日 × 想定 CTR × 型別の送客率。試験枠は「—」）
   - 推奨理由:
   - 既存記事とのつながり:
   - 比較軸:
   - 注意点:
```

最後に、必ず次を明記する。

- RAG/MCP/レポートのどれを使ったか。
- MCPが使えなかった場合は、その代替として読んだローカルファイル。
- 最有力候補を1〜2件。

## 禁止

- 既存記事・カテゴリだけを見て最終提案しない。
- `data/rag/` を直接編集しない。
- `reports/` を編集・削除しない。
- 商品追加や記事生成まで進めない。ユーザーが作成を依頼したら `kura-article-create` を使う。
