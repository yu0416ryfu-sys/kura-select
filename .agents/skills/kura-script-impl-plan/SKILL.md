# KuraSelect 実装計画書スキル

## 1. Workflow

1. 対象のファイル（script・lib・tests・テンプレ・スキル・記事など）と `package.json` を必要な範囲だけ Read する。類似の既存計画書が明示された場合のみ `docs/` も確認する。
2. 効き目の見込みに使う実績を読む（読むだけ。新たに API を叩かない）: 最新の `reports/weekly/snapshot-*.md`、`reports/affiliate-performance-log.md` の直近の行、運用の手間を減らす計画なら `docs/TODO.md` の該当行。メモリ `project_seo_lessons`・`project_*_rejected` で没案と重ならないかを確かめる（読めない環境では「メモリ未確認」と書く）。
3. `docs/IMPLEMENTATION_PLAN_{FEATURE}_{YYYY-MM-DD}.md` を作成し、§2 の節を §2 の名前と順番で置く。
4. §3 のセルフレビューを実施し、問題があれば計画書をその場で修正する。
5. §4 のとおりに締める。

---

## 2. 計画書の節（この名前・この順番）

本文:

1. **目的と効き目の見込み**: 効く先（収益ならどの段か: 検索の表示・順位・CTR → 記事の閲覧 → CTA のクリック → 成果／読者／運用／守り）、規模（数字と出典。取れなければ「見込み不明」と書き、推測で埋めない）、費用（工数・増える保守・本番のリスク・凍結や禁止日を食うか）、代わりの案（何もしなかったときに失うもの・もっと小さい案）
2. **範囲外**: 今回やらないことと理由（隣の案・後回しにした案）
3. **種類とデプロイ予定日**: `../kura-implementation-plan-review/checklist.md` §1 の記号（S / T / K / C / D / E）。本番に出るなら予定日と、`data/measurement-holds.json`（`releaseDate` > 予定日の行）・`docs/TODO.md` の禁止日（`grep -n "禁止日" docs/TODO.md`）との重なりを確かめた結果。出ないなら「本番に出ない」と理由
4. **変更方針**
5. **変更ファイルと変更箇所**
   - 既存関数の変更: 変更前/変更後のコードスニペットを両方書く
   - 新規ファイル: export する API・責務・呼び出し元の変更を書く（変更前は不要）
   - スキル・テンプレ・記事: 置き換える文を変更前/変更後で書く（節ごとなら全文）
   - 状態遷移・条件分岐: テーブルで整理する
   - 関数名・セクション名: 必ず明記する。行番号は可能な範囲で添える
   - 非対象: 影響しない記事本文・スキーマ・デプロイ設定は計画に含めない
6. **テスト**: 変更したロジックを直接 import して確かめるテスト。テストの無い種類（スキルの文面など）は「対象外」と理由
7. **実装手順**: 1計画1コミット（1デプロイ）。他の変更とコミット・push を分ける手順
8. **受入確認**: `package.json` の scripts を Read して存在するものだけ書く。`pnpm test` は基本、`pnpm build` は記事・スキーマ・フロント影響時に追加。行番号・節番号・旧い語で指した箇所の書き残しを探す grep があればそれも
9. **ロールバック**: 戻す手順と、途中で失敗したときに半端な状態が残らないか

末尾（レビュー スキルは第1巡でこの3節を読まない。名前を変えず、この順で最後に置く）:

10. **セルフレビュー**: §3 で直した点（無ければ「指摘なし」）
11. **作成者が迷っている点**: 番号つきの問い。レビューに見てほしい心配ごとはここに書き、レビューを呼ぶプロンプトには書かない。無ければ「なし」
12. **レビュー履歴**: 空の表を置く。列は `../kura-implementation-plan-review/operations.md` の「レビュー履歴」の表と同じにする

書き方:

- 本文に「（B3 反映）」のようなレビューの反映注記を書かない。レビューで直したことはレビュー履歴にだけ書く
- 件数・行数などの実測値は、測った日と方法（grep の式など）を添える

---

## 3. セルフレビュー

計画書を書いたら1項目ずつ確かめ、問題があれば計画書を直す。

1. `../kura-implementation-plan-review/checklist.md` の §1 で計画の種類を判定し（結果は §2 の3「種類とデプロイ予定日」に書く）、§3（共通）と、当てはまる種類の節の項目を当てる
2. S（スクリプト）の計画は、`checklist.md` §4 に加えて次も確かめる
   - **空値の明示性**: 空文字・null・undefined の扱いが暗黙の挙動に依存せず明示されているか
   - **責務の分離**: 状態更新・候補採用・確定判定が混在していないか

---

## 4. 締め

ユーザーには簡潔に伝える。

- 作成した計画書のパス
- 効き目の見込み（1行）
- セルフレビューで直した点（なければ「指摘なし」）
- 次の手順: `kura-implementation-plan-review` を別のコンテキスト（サブエージェントか新しいチャット）で呼ぶ。渡すのは計画書のパスと「初回」だけ（`../kura-implementation-plan-review/operations.md`）
